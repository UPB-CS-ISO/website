04. The Command Line

In the third lab you learned to redirect what a command reads and writes, and to inspect the processes of the system. In this lab you will look closer at the shell and at the terminal it runs in. You will run commands in the background, stop them and bring them back, and send them signals. You will set variables and see which of them reach the commands you start. At the end you will find out exactly what the shell does with a line of text before a command starts: how it splits it into words, what the quotes and the globs do, and how it finds the program to run.

The most important idea of this lab is that the command never sees what you type. The shell reads the line, replaces the variables and the globs, removes the quotes, sets up the redirects, finds the program and only then starts it, with a list of words as its parameters.

Objectives​

  • Understand what a terminal, a pseudo terminal and a shell are, and use the virtual terminals
  • Send signals to processes with kill command and with the keyboard, and handle a signal with trap
  • Run commands in the background and manage them as jobs with &, jobs, fg, bg and kill %N
  • See how the processes of a terminal are grouped in process groups and sessions, and keep a command running after the terminal closes with nohup
  • Use shell variables and environment variables, with export, unset, printenv and env, and the special parameters $?, $$ and $!
  • Split a command line into its parts: the assignments, the command, its parameters and the redirects
  • Use quotes and \ to control how the shell splits words and replaces variables
  • Select files with globs: *, ?, [...], [!...], ** and {...}
  • Tell built-in commands from external ones with type, and understand how the shell searches the PATH

Terminals​

In the past, a computer was shared by many users. Each of them had a terminal: a keyboard and a screen (or a printer), without a processor, connected to the computer by a cable. These terminals were TeleTypes, and Linux still calls a terminal a TTY.

The terminals only sent the keys to the computer and printed what it sent back: all the programs ran on the mainframe.

Today, the kernel gives every program that runs in a terminal a terminal device, a special file in /dev. The program reads the keys from it and writes the text to it, through the file descriptors 0, 1 and 2.

DeviceWhat it isIn ps
/dev/tty1, /dev/tty2, ...the virtual terminals of the kernel: each one uses the screen and the keyboard of the computer, one at a timetty1
/dev/pts/0, /dev/pts/1, ...the pseudo terminals: one for every terminal window or tab, and for every SSH connectionpts/0
/dev/ttynot a terminal of its own: a shortcut to the terminal of the process that opens itnever: ps shows the real one

Virtual Terminals​

A computer today has one screen and one keyboard, but the kernel makes them look like several terminals: the virtual terminals. Each one works like one of the old terminals, with its own login and its own programs, but only one of them is on the screen at a time.

The kernel shows only one of them at a time. On /dev/tty1 in the image above, agetty printed the login prompt, and after the login the shell of alice, bash, uses the same terminal. The graphical interface runs in one of the virtual terminals too, usually the first or the second one. Before you leave it, find out which one, so you know how to come back. Run this in a terminal in Sway:

[student@fedora ~]$ loginctl show-session $XDG_SESSION_ID -p VTNr
VTNr=2

loginctl asks systemd about your login session: here, Sway runs in the second virtual terminal, /dev/tty2. Ctrl+Alt+F<n> switches to the virtual terminal n:

KeysGoes to
Ctrl+Alt+F3 ... F6a text mode terminal, /dev/tty3 ... /dev/tty6
Ctrl+Alt+F2back to Sway, if VTNr is 2 (F1 if it is 1)

In a text mode terminal, a program called agetty waits for a user. Log in with your user and password: login checks them and starts your shell, bash.

fedora login: student
Password:
[student@fedora ~]$ tty
/dev/tty3
[student@fedora ~]$ exit
  • tty prints the name of the terminal of the shell: this time a virtual terminal, /dev/tty3.
  • exit closes the shell and agetty waits for a new login.
  • Ctrl+Alt+F2 goes back to Sway, with all your windows exactly as you left them: Sway kept running while you were away.
caution

In a VirtualBox virtual machine, Ctrl+Alt+F3 is caught by your own operating system, not by the virtual machine. Use Host+F3 instead (the Host key is usually the right Ctrl), and Host+F2 to go back. Other virtual machines have a menu to send these keys.

tip

If you do not know where Sway is, try Ctrl+Alt+F1 and F2. One of them is Sway; the other one shows a login screen or a text terminal.

Terminal Emulators​

The graphical interface, Xorg or Wayland (Sway is a Wayland compositor), takes over one of the virtual terminals and draws on the screen through the framebuffer of the kernel. In it, a terminal is a graphical application, a terminal emulator: foot, kitty, ptyxis, alacritty, ghostty, ... Each window of a terminal emulator asks the kernel for a pseudo terminal: it opens /dev/ptmx, and the kernel creates a new /dev/pts/<n>.

A pseudo terminal has two ends. The terminal emulator keeps one end, the master, and reads and writes it like a file. The other end, the slave, is the file /dev/pts/<n>: it behaves exactly like a real terminal. When the emulator starts the shell, it redirects /dev/pts/<n> as the 0, 1 and 2 of the shell.

The keys you press are written by the emulator into the master, and the shell reads them from the slave. What the shell writes into the slave comes out of the master, and the emulator draws it in its window. The shell does not know that there is a window: it only sees a terminal.

[student@fedora ~]$ tty
/dev/pts/0
[student@fedora ~]$ ps
    PID TTY          TIME CMD
   2817 pts/0    00:00:00 bash
   3104 pts/0    00:00:00 ps
[student@fedora ~]$ ls /dev/pts
0  1  ptmx
[student@fedora ~]$ ls -l /proc/$$/fd/0
lrwx------. 1 student student 64 Oct 20 10:02 /proc/2817/fd/0 -> /dev/pts/0
  • This shell runs in the first terminal window, /dev/pts/0, and ps shows only the processes of this terminal.
  • There are two windows open, so there are two pseudo terminals, 0 and 1.
  • The standard input of the shell is the pseudo terminal, as you saw in lab 03.
tip

A pseudo terminal is a file: what you write into it appears in the window of that terminal. With two terminals, echo hello > /dev/pts/1 run in the first one writes hello in the second one.

Signals​

A signal is a short message that the operating system sends to a process: a number, with a name that starts with SIG. When a signal arrives, the process stops what it is doing and runs the default action of the signal, or, if it has one, its own signal handler, and then continues.

Default actionWhat happens to the process
Termit ends
Coreit ends and leaves a copy of its memory (a core dump), for debugging
Stopit is paused, until it receives SIGCONT
Contit continues, if it was stopped; otherwise nothing happens
Ignnothing, the signal is thrown away
info

On Fedora, the core dumps do not appear as files in the current directory: systemd-coredump keeps them. coredumpctl list shows them, the newest last.

Sending a Signal: kill​

Despite its name, kill sends a signal. Only SIGTERM, its default, asks the process to end.

CommandWhat it does
kill -lLists all the signals, with their numbers
kill -l <NUMBER>Prints the name of a signal: kill -l 15 prints TERM
kill <PID>Sends SIGTERM, the default, to the process
kill -KILL <PID>Sends SIGKILL; kill -9 <PID> and kill -SIGKILL <PID> are the same
kill -STOP <PID>Stops the process
kill -CONT <PID>Continues the stopped process
kill <PID1> <PID2> ...Sends the signal (SIGTERM, or the one you give) to several processes
kill %<N>Sends the signal to job N of this shell (see jobs)

Start sleep 1000 in the second terminal and send it signals from the first one:

[student@fedora ~]$ pgrep sleep
3150
[student@fedora ~]$ kill -STOP 3150
[student@fedora ~]$ ps -o pid,stat,cmd -p 3150
    PID STAT CMD
   3150 T+   sleep 1000
[student@fedora ~]$ kill -CONT 3150
[student@fedora ~]$ ps -o pid,stat,cmd -p 3150
    PID STAT CMD
   3150 S+   sleep 1000
[student@fedora ~]$ kill 3150
[student@fedora ~]$ ps -o pid,stat,cmd -p 3150
    PID STAT CMD
  • SIGSTOP paused sleep: its state became T (stopped).
  • SIGCONT continued it: it is waiting again (S).
  • SIGTERM ended it: ps finds no process with this PID, and the second terminal prints Terminated.
caution

Use kill -KILL only when kill alone does not work. SIGTERM lets a program clean up before it ends (save its files, delete its temporary files), SIGKILL does not give it any chance.

Keys That Send Signals​

The terminal turns some keys into signals for the process that runs in the foreground, the one that reads the keyboard:

KeysSendsWhat happens, by default

Ctrl+\SIGQUITthe foreground job ends, and the system saves a core dump
Ctrl+ZSIGTSTPthe foreground job is stopped, and the shell shows the prompt (see below)
Ctrl+Dno signalat the start of a line, end of file: the program reads nothing more
[student@fedora ~]$ sleep 100

[student@fedora ~]$ sleep 100

[student@fedora ~]$ sleep 100

[1]+  Stopped                 sleep 100
info

Ctrl+D at the prompt of the shell is the end of its input: the shell ends, and the terminal window closes.

Handling a Signal: trap​

A program can replace the default action of a signal with its own signal handler: a part of its code that runs when the signal arrives, instead of the default action. A bash script sets a handler with trap, which runs a command or a function.. Create the file ~/lab04/stubborn.sh with nano:

#!/bin/bash

# the signal handler
function no_interruptions_please () {
    echo "No interruptions please"
}

# register the signal handler
trap no_interruptions_please SIGINT

while true; do
    echo "working"
    sleep 1
done
[student@fedora lab04]$ bash stubborn.sh
working
working
^CNo interruptions please
working
^CNo interruptions please
working
^\Quit (core dumped)
  • The script writes working every second, forever.
  • Ctrl+C sends SIGINT: the script runs its handler, prints the message, and keeps working.
  • Ctrl+\ sends SIGQUIT, which has no handler: the script ends.
CommandWhat it does
trap '<command>' <SIGNAL>Runs command when SIGNAL arrives; the quotes make it one word
trap '' <SIGNAL>Ignores the signal
trap - <SIGNAL>Goes back to the default action
trap -pPrints the handlers
info

trap keeps the handler as text, and the shell runs that text when the signal arrives, as if you typed it then. The quotes decide when a variable in it is replaced:

info

SIGKILL and SIGSTOP cannot be handled or ignored: trap cannot change them. This is why kill -KILL always ends a process.

Foreground and Background​

A terminal has one job in the foreground: it reads the keyboard and receives the signals of the keys, and the shell waits for it to end before it shows the prompt again. All the commands you ran so far ran in the foreground.

The shell can also start commands in the background. They are called jobs: the shell does not wait for them and shows the prompt right away, so they run at the same time as the commands you type. A job is either running or stopped.

A command starts in the foreground (cmd) or in the background (cmd &). Ctrl+Z stops the foreground process and moves it to the background, bg continues a stopped job in the background, and fg brings a job back to the foreground. The rest of this section shows each of them.

Starting a Job: &​

Put & at the end of a command to run it in the background:

[student@fedora ~]$ sleep 100 &
[1] 4242
[student@fedora ~]$ sleep 200 &
[2] 4250
[student@fedora ~]$ jobs
[1]-  Running                 sleep 100 &
[2]+  Running                 sleep 200 &
[student@fedora ~]$ echo $!
4250
[student@fedora ~]$ kill %1
[student@fedora ~]$
[1]-  Terminated              sleep 100
  • [1] is the job ID, which exists only in this shell; 4242 is the PID, for the whole system.
  • jobs lists the jobs of this shell: + marks the current job (the last one), - the previous one.
  • $! is the PID of the last job started with &.
  • %1 means job 1: kill %1 sent SIGTERM to it, and the shell said that it ended when it showed the next prompt.
CommandWhat it does
command &Runs command in the background, as a job
jobsLists the jobs of this shell
jobs -lLists them with their PIDs
fg %<N>Brings job N to the foreground (and continues it, if it is stopped)
bg %<N>Continues the stopped job N in the background
kill %<N>Sends SIGTERM to job N
fg, bgWithout %<N>, they work on the current job, the one with +
caution

A job still writes to the same terminal: its output gets mixed with the commands you type. Redirect its output, for example find / -name passwd > found.txt 2> /dev/null &.

Stopping and Continuing: fg and bg​

A command that runs in the foreground can be moved to the background later:

  1. press Ctrl+Z: the command is stopped (SIGTSTP), and the shell prints its job ID, for example [1]+ Stopped, and shows the prompt;
  2. find its job ID with jobs;
  3. run bg %<N>: the job continues (SIGCONT) in the background.
tip

fg %<N> brings it back to the foreground.

[student@fedora ~]$ sleep 100 > /dev/null
^Z
[1]+  Stopped                 sleep 100 > /dev/null
[student@fedora ~]$ jobs
[1]+  Stopped                 sleep 100 > /dev/null
[student@fedora ~]$ bg %1
[1]+ sleep 100 > /dev/null &
[student@fedora ~]$ jobs
[1]+  Running                 sleep 100 > /dev/null &
[student@fedora ~]$ fg %1
sleep 100 > /dev/null
^C
  • After Ctrl+Z, sleep is stopped and the shell shows the prompt.
  • bg continued it in the background (the shell prints it with an & at the end).
  • fg brought it back to the foreground: the shell waits for it again, and Ctrl+C reaches it.
tip

Ctrl+Z is useful when you forgot the &, or when you want to leave a program for a moment, for example nano or less, run a command, then go back with fg.

Jobs That Read the Keyboard​

Only the foreground process can read the keyboard. A job that tries to read it receives SIGTTIN and is stopped:

[student@fedora ~]$ cat &
[1] 4321
[student@fedora ~]$
[1]+  Stopped                 cat
[student@fedora ~]$ fg
cat
hello
hello
^D

cat without parameters reads the keyboard, so it stopped right away. fg brought it to the foreground, where it can read: it printed back every line, until Ctrl+D.

info

You cannot close a shell that still has stopped jobs at the first try: exit prints There are stopped jobs., and only a second exit closes it (and ends the jobs).

Sessions and Process Groups​

The kernel groups the processes of a terminal in two levels:

GroupWhat it isIts ID: the PID of its leaderIts leader
process groupone job: all the processes of one command line, sleep 100 | cat is one group of two processesPGID: the first process of the command linethe group leader
sessionall the process groups of one terminalSID, the PID of the shellthe session leader: the shell, s in STAT

The terminal is the controlling terminal of the session. Its input, and the signals of the keys (Ctrl+C, Ctrl+Z, ...), go to the foreground process group, so they reach every process of the foreground job. + in the STAT column of ps marks the processes of the foreground group.

[student@fedora ~]$ echo $$
3000
[student@fedora ~]$ sleep 100 | cat &
[1] 4243
[student@fedora ~]$ ps -o pid,ppid,pgid,sid,tty,stat,comm
    PID    PPID    PGID     SID TT       STAT COMMAND
   3000    2990    3000    3000 pts/0    Ss   bash
   4242    3000    4242    3000 pts/0    S    sleep
   4243    3000    4242    3000 pts/0    S    cat
   4250    3000    4250    3000 pts/0    R+   ps
  • bash is the session leader: its PID is the SID of all the processes of the terminal, and it has an s in STAT.
  • sleep and cat are one job, so one group: 4242, the PID of sleep, the first process of the job.
  • ps runs in the foreground (+), in a group of its own.

Closing the Terminal: SIGHUP and nohup​

When the terminal closes, the kernel sends SIGHUP (hang up) to the session leader, the shell. The shell sends SIGHUP to all its jobs, and they end. A command started with nohup ignores SIGHUP, so it keeps running:

[student@fedora ~]$ sleep 1000 &
[1] 4300
[student@fedora ~]$ nohup sleep 2000 > /dev/null &
[2] 4301
nohup: ignoring input

Close this terminal window, and look for the two jobs from another terminal:

[student@fedora ~]$ pgrep -a sleep
4301 sleep 2000
[student@fedora ~]$ ps -o pid,ppid,sid,tty,comm -p 4301
    PID    PPID     SID TT       COMMAND
   4301       1    3000 ?        sleep
  • sleep 1000 received SIGHUP and ended.
  • sleep 2000 ignored it and keeps running, without a terminal (?); its parent ended, so its new parent is PID 1.
info

If you do not redirect its output, nohup writes it into the file nohup.out, because the terminal will not exist anymore: nohup: ignoring input and appending output to 'nohup.out'.

caution

If the shell is killed with SIGKILL, it cannot send SIGHUP to its jobs anymore: they keep running, without a terminal, even without nohup.

Environment Variables​

Every process has an environment: a list of variables, each written as NAME=value. Programs read it to configure themselves: HOME tells them the home directory of the user, LANG the language, and PATH where to look for programs. The names are case-sensitive (HOME and home are different variables) and, by convention, in UPPER CASE.

A process receives its environment from its parent when it starts: usually a copy of the parent's environment. From then on the two are separate: a change in one does not reach the other.

CommandWhat it does
printenvPrints all the environment variables
printenv <NAME>Prints the value of one variable
envPrints all the environment variables, like printenv
echo $NAMEThe shell replaces $NAME with its value, then echo prints it
[student@fedora ~]$ printenv HOME
/home/student
[student@fedora ~]$ echo "I am $USER, my shell is $SHELL"
I am student, my shell is /bin/bash
[student@fedora ~]$ env | wc -l
35

Shell Variables and export​

The shell has two kinds of variables:

  • shell variables: they exist only inside this shell;
  • environment variables: they are part of the environment, so every command started from this shell receives a copy.
SyntaxWhat it does
NAME=valueCreates a shell variable, or changes the value of an existing variable
export NAMEMakes the variable an environment variable: every command started from now on receives it
export NAME=valueBoth at once
NAME=value commandAn environment variable only for command; the shell does not keep it
unset NAMEDeletes the variable, from the shell and from the environment
$NAMEReplaced by the shell with the value, or with nothing if the variable does not exist
${NAME}The same, with clear limits: "${NAME}_old" is the value followed by _old; "$NAME_old" is the variable NAME_old
[student@fedora ~]$ GREETING=hello
[student@fedora ~]$ echo $GREETING
hello
[student@fedora ~]$ bash -c 'echo "child: $GREETING"'
child:
[student@fedora ~]$ export GREETING
[student@fedora ~]$ bash -c 'echo "child: $GREETING"'
child: hello
[student@fedora ~]$ unset GREETING
[student@fedora ~]$ echo "[$GREETING]"
[]
  • GREETING=hello created a shell variable, and the shell replaced $GREETING with hello.
  • bash -c '...' starts a new shell, a child, that runs the text between the quotes. The child did not receive GREETING: it was not part of the environment.
  • After export, the child received a copy of it.
  • After unset, the variable does not exist anymore, and $GREETING is replaced with nothing.
danger

No spaces around =. GREETING = hello runs the command GREETING, with the parameters = and hello: bash: GREETING: command not found. Put the value between quotes when it has spaces: GREETING="good morning".

info

A process can change only its own environment, and the environment of the children it starts after that. A child can never change a variable of its parent: this is why export and unset are commands of the shell, not programs.

A Variable for One Command​

NAME=value written before a command puts the variable only in the environment of that command:

[student@fedora ~]$ date +%H:%M
11:47
[student@fedora ~]$ TZ=Asia/Tokyo date +%H:%M
18:47
[student@fedora ~]$ echo "[$TZ]"
[]
[student@fedora ~]$ ls /nope
ls: cannot access '/nope': No such file or directory
[student@fedora ~]$ LANG=ro_RO.UTF-8 ls /nope
ls: nu se poate accesa '/nope': Fișier sau director inexistent
  • TZ (time zone) changed the time zone only for that date; the shell did not keep it.
  • LANG changed the language of the messages of ls (if the Romanian language is installed).

Variables Defined by the System​

When the prompt shows up, the shell already has many variables, set when you logged in or by its startup files:

VariableValue
HOMEyour home directory, ~
USERyour user name
SHELLyour shell, from /etc/passwd
PWD, OLDPWDthe current directory and the previous one (cd - goes to OLDPWD)
PATHthe directories with the programs, separated by : (see The PATH Search)

PS1the prompt; a shell variable, not exported
tip

PS1 is the text of the prompt, with some special sequences: \u is the user, \h the computer, \w the current directory, \$ is $ (or # for root). Try PS1='\u in \w \$ '. The change lasts until you close the terminal.

Special Parameters: $?, $$ and $!​

The shell sets a few more values that you can only read:

ParameterValue
$?the exit code of the last command: 0 means success, anything else an error
$$the PID of the shell
$!the PID of the job most recently sent to the background, with & or bg
[student@fedora ~]$ ls /nope
ls: cannot access '/nope': No such file or directory
[student@fedora ~]$ echo $?
2
[student@fedora ~]$ echo $?
0

ls failed, with the exit code 2. The second echo $? prints the exit code of the first echo, which succeeded: $? changes after every command.

The Command Line​

Before a command starts, the shell reads the whole line and splits it into parts:

[student@fedora lab04]$ LANG=C sort -r "$HOME/my notes.txt" my\ list.txt *.csv > sorted.txt 2> errors.txt
PartIn the exampleWhat it is
assignmentsLANG=CNAME=value words at the start: variables only for this command
the commandsortthe first word that is not an assignment or a redirect
the parameters-r, "$HOME/my notes.txt", my\ list.txt, *.csveverything else: options, file names, texts
redirects> sorted.txt, 2> errors.txta redirect and the word after it; they are for the shell, not for the command, and can be anywhere

Then, step by step:

  1. it splits the line into words at the spaces, except inside quotes and after a \;
  2. it sets apart the assignments and the redirects;
  3. it replaces $NAME and ~ with their values;
  4. it splits again the values of the variables that were not between quotes;
  5. it expands the globs (*.csv) into the names of the matching files;
  6. it removes the quotes and the \;
  7. it sets up the redirects and runs the command, with the words that are left as its parameters.

sort receives 5 parameters: -r, /home/student/my notes.txt, my list.txt, a.csv and b.csv. It never sees the quotes, the $, the * or the redirects.

tip

To see the words that a command receives, use printf '[%s]\n' instead of the command: it prints every parameter between brackets, on its own line.

[student@fedora lab04]$ printf '[%s]\n' -r "$HOME/my notes.txt" my\ list.txt *.csv
[-r]
[/home/student/my notes.txt]
[my list.txt]
[a.csv]
[b.csv]

The Order of Redirects​

The redirects can be written anywhere in the line, even before the command, and the shell applies them from left to right:

[student@fedora lab04]$ 2> errors.txt ls > list.txt /nope .
[student@fedora lab04]$ ls /nope > all.txt 2>&1
[student@fedora lab04]$ ls /nope 2>&1 > all.txt
ls: cannot access '/nope': No such file or directory
  • The first line is the same as ls /nope . > list.txt 2> errors.txt.
  • > all.txt 2>&1: first 1 goes to all.txt, then 2 goes where 1 goes now, also into all.txt.
  • 2>&1 > all.txt: first 2 goes where 1 goes now, the display, then only 1 changes to all.txt. The error is on the display.

Quoting and Escaping​

Some characters have a special meaning for the shell: the space, $, *, ?, [, {, ~, >, <, |, &, ;, #, ', " and \. Quotes and \ turn the special meaning off:

Written asWhat it does
'...'single quotes: everything inside is plain text, nothing is replaced
"..."double quotes: $NAME is still replaced, but the result stays one word; globs are not expanded
\the next character is plain text: \ is a space that does not split, \$ is a $

With NAME="Alice Smith" (three spaces), this is what echo receives:

You typeecho receivesWhy
echo $NAMEAlice, Smithno quotes: replaced, then split at the spaces
echo "$NAME"Alice Smithdouble quotes: replaced, one word, the spaces are kept
echo '$NAME'$NAMEsingle quotes: nothing is replaced
echo \$NAME$NAME\$: the $ is just a character
echo my\ file.txtmy file.txt\ : the space does not split
echo "\$NAME is $NAME"$NAME is Alice Smithinside "...", \$ is a $, $NAME is replaced
echo "it's" 'say "hi"'it's, say "hi"each kind of quotes protects the other one
echo 'a\b'a\binside '...', \ is just a character
[student@fedora ~]$ NAME="Alice   Smith"
[student@fedora ~]$ echo $NAME
Alice Smith
[student@fedora ~]$ echo "$NAME"
Alice   Smith
[student@fedora ~]$ printf '[%s]\n' $NAME
[Alice]
[Smith]

tip

Put every variable between double quotes, "$NAME", unless you really want it split into words. A file name with a space in a variable breaks a command without them: rm $FILE with FILE="my notes.txt" tries to delete my and notes.txt.

Globbing​

A glob is a pattern for file names. The shell replaces it with the names of the matching files, in alphabetical order, before the command starts. In this directory:

[student@fedora glob]$ ls
docs  notes.txt  photo1.png  photo2.png  photo3.png  photoA.png  report.md  todo.txt
GlobMatchesecho receives
*.txt*: any characters, or none (but not /)notes.txt, todo.txt
photo?.png?: exactly one characterphoto1.png, photo2.png, photo3.png, photoA.png
photo[12].png[12]: one character, 1 or 2photo1.png, photo2.png
photo[0-9].png[0-9]: one character in the rangephoto1.png, photo2.png, photo3.png
photo[!0-9].png[!0-9]: one character not in the range ([^0-9] also works)photoA.png
docs/**/*.txt**: any directories, at any depth (needs shopt -s globstar)docs/2026/exam.txt, docs/plan.txt
{a,b,c}.pdf{...}: one word for each, even if the file does not exista.pdf, b.pdf, c.pdf
*.pdfno file matches*.pdf, the glob as it is
caution

When no file matches, bash gives the glob as it is to the command: ls *.pdf prints ls: cannot access '*.pdf': No such file or directory. Other shells, like zsh, print an error and do not run the command at all.

info
  • * and ? do not match the . at the beginning of a hidden file: * does not include .bashrc, but .* does.
  • {...} is not a glob: it makes the words even if there are no files, which is useful to create them, for example mkdir -p 2026/{jan,feb,mar} or touch photo{4..6}.png ({4..6} is 4 5 6).
  • ** works only after shopt -s globstar; without it, it is the same as *.
  • Between quotes, a glob is plain text: echo "*.txt" prints *.txt. This is how you give a pattern to a command that understands it by itself, like find . -name "*.txt".

Running a Command​

Built-in and External Commands​

Not every command is a program:

KindWhat it isExamplesHelp
built-in commandpart of the shell: it runs inside it, without a new processcd, export, unset, exit, jobs, fg, bg, trap, typehelp <name>
some are built in only to be faster, and also exist as programsecho, printf, kill, pwd
external commandan executable file on the disk, found in PATH; the shell starts it as a child processls, sort, grep, sleep, bashman <name>

type tells which one a command is:

[student@fedora ~]$ type cd
cd is a shell builtin
[student@fedora ~]$ type sort
sort is /usr/bin/sort
[student@fedora ~]$ type ls
ls is aliased to `ls --color=auto'
[student@fedora ~]$ type -a echo
echo is a shell builtin
echo is /usr/bin/echo
  • cd is built in, sort is the file /usr/bin/sort.
  • ls is an alias: a short name for another command line, here ls --color=auto.
  • -a shows all the meanings of the name: echo is built in, and there is also a program with the same name. The shell uses the first one.
info

cd, export, unset and exit must be built in: they change the shell itself, its current directory, its variables, or stop it. A program started by the shell is a child process, and a child cannot change its parent.

The PATH Search​

The kernel can only start a program from its path. When the first word is a name, the shell has to find the file:

  1. if the word has a /, it is a path: absolute (/usr/bin/sort) or relative to the current directory (./hello, bin/hello, ../tools/hello), used as it is;
  2. otherwise, if it is an alias or a built-in command, the shell runs it itself;
  3. otherwise, the shell searches the directories of the PATH variable, from left to right, and runs the first file with that name;
  4. if no directory has it: command not found.
[student@fedora ~]$ echo $PATH
/home/student/.local/bin:/home/student/bin:/usr/local/bin:/usr/bin
[student@fedora ~]$ cd ~/lab04
[student@fedora lab04]$ ls bin
hello
[student@fedora lab04]$ hello
bash: hello: command not found
[student@fedora lab04]$ bin/hello
Hello!
[student@fedora lab04]$ PATH="$PATH:$HOME/lab04/bin"
[student@fedora lab04]$ hello
Hello!
[student@fedora lab04]$ type hello
hello is /home/student/lab04/bin/hello
  • The shell does not look in the current directory, so hello alone was not found.
  • bin/hello has a /, so it is a path, and the shell ran it.
  • After adding ~/lab04/bin at the end of PATH, the shell found hello there.
caution

Add directories to PATH, never replace it: PATH=~/lab04/bin alone leaves the shell without /usr/bin, and ls, cat and almost every other command become command not found. Close the terminal and open a new one to get the old PATH back.

tip

On Fedora, ~/.local/bin and ~/bin are already in PATH: copy a program of your own there and it works from any directory, in every new terminal.

    3. create photo4.png, photo5.png and photo6.png with one touch and a {...} range;
    4. print the hidden files of your home directory with echo ~/.*, and check whether the list has . and ..; find the shopt option that decides this in man bash.

    Check: the first list has docs/2026/exam.txt, docs/plan.txt, notes.txt and todo.txt; photo?.png now matches 7 files; ~/.* has .bashrc and the other hidden files, but not . and ..: the option globskipdots is on by default since bash 5.2. → Globbing

  24. Glob or text: In ~/lab04/glob:

    1. run find . -name *.txt;
    2. run find . -name "*.txt";
    3. find out why the first one fails, using printf '[%s]\n' instead of find.

    Check: without quotes, the shell replaced *.txt with notes.txt todo.txt before find started, so find received the wrong parameters (find: paths must precede expression); with quotes, find received the pattern and found all 4 files. → Globbing

  25. Run a program from a directory: In ~/lab04:

    1. run hello;
    2. run it with a relative path, then with an absolute path;
    3. go to ~/lab04/bin and run it from there;
    4. add ~/lab04/bin at the end of PATH, go to your home directory and run hello.

    Check: hello alone is command not found, but bin/hello, /home/student/lab04/bin/hello and, in bin, ./hello work; after the change of PATH, hello works from any directory, and type hello shows its path (hello is hashed (...), because you already ran it). → The PATH Search

  26. A broken PATH: Open a new terminal:

    1. set PATH to /tmp, and run ls;
    2. run /usr/bin/ls;
    3. run cd ~ and echo $HOME;
    4. close the terminal.

    Check: ls is command not found, but /usr/bin/ls works, because it is a path; cd and echo still work, because they are built in. → The PATH Search

  27. Your own bin:

    1. create ~/.local/bin, if it does not exist, and copy bin/hello there;
    2. open a new terminal and run hello from your home directory;
    3. find out from where it was started.

    Check: type hello prints hello is hashed (/home/student/.local/bin/hello): on Fedora, this directory is already in PATH. → The PATH Search

  28. Who wins:

    1. create the directory ~/lab04/first with two programs, ls and echo, that print Not the real ls! and Not the real echo! (do as for bin/hello in exercise 1: printf with single quotes, then chmod +x);
    2. add ~/lab04/first at the beginning of PATH;
    3. run ls, \ls, /usr/bin/ls and echo hi;
    4. run type -a ls and type -a echo;
    5. close the terminal.

    Check: ls and \ls (which skips the alias) both print Not the real ls!: the alias only replaces the word ls with ls --color=auto, and this ls is still searched in PATH, where ~/lab04/first comes first. /usr/bin/ls is a path, so there is no search. echo hi prints hi: a built-in command comes before the PATH search. type -a lists the meanings in the order the shell tries them. → The PATH Search

📝 Challenges​

  1. Ignore and restore:

    1. edit stubborn.sh so that it also ignores SIGTERM;
    2. run it in the second terminal, and try to end it from the first terminal with kill, then with kill -KILL;
    3. in your shell, make SIGINT print Not now, press Ctrl+C at the prompt, then go back to the default action.

    Check: kill does nothing to the script, kill -KILL ends it; trap -p shows the handler of your shell before you remove it. → Handling a Signal

  2. Kill the shell:

    1. open a new terminal, and start sleep 1000 & and sleep 2000 & in it;
    2. print the PID of this shell;
    3. from another terminal, end this shell with SIGKILL;
    4. list the processes of the session of the killed shell (look in man ps for the option that selects a session), with the columns pid, ppid, sid, tty and comm;
    5. end the two sleep processes.

    Check: the window closed, but both sleep processes are still running, without a terminal; their new parent is PID 1, or a process that adopts orphans, like systemd --user. The shell could not send SIGHUP to them. → Closing the Terminal

  3. A session in text mode:

    1. log in on /dev/tty3 (Ctrl+Alt+F3) and start sleep 1000 &;
    2. go back to Sway, and list the processes of that terminal with ps -t tty3 -o pid,ppid,sid,stat,comm;
    3. find the session leader of tty3, and its parent;
    4. go back to tty3, end sleep, and log out.

    Check: bash is the session leader: it has s in STAT, and its PID is the SID of sleep; its parent is login, which checked your password and started it. → Virtual Terminals · Sessions and Process Groups

  4. Why cd is built in: Fedora also has a program called cd, in /usr/bin.

    1. find it with type -a cd;
    2. go to your home directory, run /usr/bin/cd /tmp, and print the current directory;
    3. explain what happened.

    Check: the current directory is still your home directory: /usr/bin/cd ran as a child process and changed only its own current directory, then ended. → Built-in and External Commands

  5. Your own alias:

    1. add the line alias lt='ls -lt' at the end of ~/.bashrc, with nano;
    2. run lt in the same terminal, then in a new terminal;
    3. in the old terminal, run source ~/.bashrc, and try lt again;
    4. find out with type what lt is.

    Check: in the old terminal, lt is command not found at first: bash reads ~/.bashrc only when it starts, or when you ask it to with source; in the new terminal, and after source, lt lists the files, the newest first, and type prints lt is aliased to `ls -lt'. → Built-in and External Commands

  6. An empty environment: Look in man env for the option that starts a command with an empty environment.

    1. run env with this option, followed by bash -c 'echo "[$HOME] [$PATH]"';
    2. run env with this option, followed by bash -c 'ls';
    3. run env with this option, followed by TZ=Asia/Tokyo /usr/bin/date.

    Check: HOME is empty, PATH has a default value that bash sets by itself, so ls still works; date prints the time in Tokyo: the only variable it received is TZ. → Environment Variables

  7. Background PIDs:

    1. start sleep 300 | sleep 400 in the background;
    2. print $!, and list the jobs with their PIDs;
    3. end the whole job with one kill, using the job ID.

    Check: $! is the PID of sleep 400, the last process of the pipe; jobs -l shows both PIDs; kill %1 ends both processes, because it sends the signal to the whole process group. → Starting a Job · Sessions and Process Groups

  8. Count with globs: Go to /usr/bin and, without ls or find, using only a glob:

    1. print, one per line, the programs whose name starts with g and has exactly 4 characters (use printf '%s\n');
    2. count them, in the same command line;
    3. do the same for the programs whose name ends with a digit;
    4. go back to ~/lab04.

    Check: the first count is the same as find /usr/bin -maxdepth 1 -name 'g???' | wc -l; the first list has gzip and grep, and the third one has python3. → Globbing · Pipes

  9. Another shell:

    1. install zsh with sudo dnf install zsh, and start it by typing zsh (if it shows a configuration menu, press q);
    2. in ~/lab04/glob, run echo *.pdf and echo docs/**/*.txt;
    3. set NAME="Alice Smith" and run printf '[%s]\n' $NAME;
    4. leave zsh with exit, open a new terminal (so that globstar is off), go to ~/lab04/glob, set NAME again and run the same three commands in bash.

    Check: zsh prints zsh: no matches found: *.pdf and does not run echo; it understands ** without any option, and it does not split $NAME into words. bash prints *.pdf, only docs/2026/exam.txt (without globstar, ** is *), and two words. → Globbing · Quoting and Escaping

  10. The exit code of a signal:

    1. run sleep 100, stop it with Ctrl+C, and print the exit code;
    2. do the same with Ctrl+\;
    3. run bash -c 'kill -KILL $$' (a shell that sends SIGKILL to itself) and print the exit code.

    Check: the exit codes are 130, 131 and 137: a process ended by a signal has the exit code 128 + the number of the signal (2, 3 and 9). → Special Parameters · Signals

  11. Clean up:

    1. end all your sleep processes with one command (look in man pkill for how to match the exact name);
    2. delete ~/.local/bin/hello, ~/lab04/first, ~/lab04/trips, glob/photo4.png, glob/photo5.png, glob/photo6.png, found.txt, list.txt, errors.txt, all.txt and sorted.txt with one rm command, without errors for the ones that do not exist (use {...} for the photos);
    3. remove the lt alias from the end of ~/.bashrc, with nano.

    Check: pgrep sleep prints nothing, ls ~/lab04 shows only the files from exercise 1, and ls ~/lab04/glob shows the same 7 names as before exercise 46. → Managing Files

Wrap-up Questions​

Use the last 5 minutes of the lab to answer these questions together with your colleagues and the teaching assistant. There are no wrong answers for the last two.

  1. What is the difference between a terminal, a terminal emulator and a shell?
  2. What is the difference between SIGTERM and SIGKILL? Why can't SIGKILL be handled?
  3. What happens when you press Ctrl+C, Ctrl+Z and Ctrl+D?
  4. What is the difference between a job ID and a PID?
  5. Why do the jobs of a terminal end when you close it? How can you keep one running?
  6. What is the difference between a shell variable and an environment variable?
  7. Why can't a child process change a variable of its parent?
  8. What is the difference between "$NAME" and '$NAME'?
  9. Why does the shell not run a program from the current directory without ./?
  10. Which of the keys, globs or shortcuts from this lab will you use most often?
