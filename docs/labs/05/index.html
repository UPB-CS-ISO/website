05. Users and Permissions

In the fourth lab you learned what the shell does with a command line, and how it starts the programs and sends them signals. In this lab you will find out with which user id these programs are running. You will look at the users and the groups of the system, at the files that keep them, /etc/passwd, /etc/shadow and /etc/group, and at how the system checks a password without ever storing it. You will run commands as root with sudo, create new users, and then decide who may read, write and run your files, with chmod, chown and umask. At the end you will meet the special permissions: the setuid bit that lets passwd change your password, the setgid bit for shared directories and the sticky bit of /tmp.

The most important idea of this lab is that the kernel does not know any names. Every process carries a label, the number of its user (the UID) and the numbers of its groups, and every file has an owner, a group and three sets of permissions. Every time a process opens a file, the kernel compares the two. The most important idea of this lab is that the kernel does not know any names, only numbers. Every process carries a label: the number of its user (the UID) and the numbers of its groups (the GIDs). Every file keeps the number of its owner, the number of its group, and three sets of permissions: for the owner, for the group and for everybody else. Every time a process opens a file, the kernel compares the label of the process with the owner and the group of the file, picks one of the three sets, and checks if it allows what the process asks for.

Objectives​

  • Understand what a user and a group are for the kernel: a UID and a GID
  • Find out who you are with whoami, id and groups, and which user runs every process with ps
  • Understand the credentials of a process, its real, effective and saved UID, which of them the kernel checks, and when they change
  • Read the users database, /etc/passwd, and the groups database, /etc/group, with getent
  • Understand how /etc/shadow keeps the passwords as hashes with salt, and how a password is checked
  • Understand what happens when you log in: agetty, login and the shell
  • Run commands as root, or as another user, with sudo and su, and avoid the redirect trap with tee
  • Create, change and delete users and groups with useradd, passwd, usermod, groupadd, gpasswd and userdel
  • Read the permissions of a file with ls -l and stat, and understand r, w and x for files and directories
  • Change the permissions with chmod (letters and numbers), the owner with chown and chgrp, and the default permissions with umask
  • Use the special permissions: setuid, setgid and the sticky bit
  • Understand why the prompt cannot be trusted to tell who you are

Users​

For you, a user is a name, like student. For the kernel, a user is only a number, the UID (User ID). Every process carries the UID of the user that started it, as a label, for its whole lifetime, and a child process inherits the label of its parent. When a process asks the kernel to do something, to open a file or to send a signal, the kernel looks at this label and decides if the process is allowed to do it.

Users are not only people. Many services of the system run as a user of their own: if one of them has a bug, or is attacked, it can only touch its own files, not the files of the other services or of the people.

The Credentials of a Process​

The label of a process is more than one UID and a list of groups. For every process, the kernel keeps a small record, the credentials of the process: four UIDs, four GIDs and the list of the supplementary groups. Think of it as an ID card that the kernel keeps for the process: the kernel looks at it every time the process asks for something, and the process cannot change it as it likes.

CredentialWhat it is
real UID and GIDthe user who started the process, and their primary group; programs read them to find out who you are
effective UID and GIDthe ones that the kernel checks, when the process opens a file or sends a signal
saved UID and GIDa spare copy of the effective ones, made when the program starts, so that it can put its rights aside for a while and take them back
file system UID and GIDused only for files; on Linux, they always follow the effective ones, so you can ignore them
supplementary groupsthe other groups of the process, checked together with the effective GID; copied from the groups database at login, and by su and sudo
note

For your shell, the four UIDs are all 1000 and the four GIDs are all 1000. Why does the kernel keep four copies of the same number? Because they are not always the same: a program with the setuid bit, like passwd, changes the effective and the saved UID, but keeps the real one. login, su and sudo do something else: they change all of them, for the shell or the command that they start.

Which Credentials Are Checked​

The kernel does not look at all the credentials every time. It depends on what the process asks for:

  • opening a file: the effective UID is compared with the owner of the file, and the effective GID and the supplementary groups with the group of the file (see Which Permissions Apply?);
  • sending a signal, with kill: the real or the effective UID of the sender must be the real or the saved UID of the target. You can end a passwd that you started, even if it runs as root, because its real UID is yours; bob cannot;
  • changing its own UIDs: a process that is not root may only take a UID that it already has, its real, its effective or its saved one. A process cannot make itself root. Only a process whose effective UID is 0 may take any UID.

How the Credentials Change​

A process gets its credentials from its parent. This table shows what happens to them at each step of the life of a process, and the only two cases that change them:

WhenWhat happens to the UIDs
fork, a new childthe child gets a copy of the credentials of its parent
exec of a regular programnothing changes
exec of a program with the setuid bitthe effective and the saved UID become the owner of the executable file; the real UID is inherited from the parent process; the setgid bit does the same for the GIDs, with the group of the file (see setuid)
a process whose effective UID is 0 calls setgid(), initgroups() and setuid()all the GIDs, the supplementary groups and all the UIDs change, in this order: this is how login, su and sudo give a process the label of a user (see Logging In and sudo)

The Users Database​

/etc/passwd​

The local users are kept in /etc/passwd, a text file with one user on every line, and the fields separated by :. Everyone can read it, because every program that shows a user name needs it.

[student@fedora ~]$ ls -l /etc/passwd
-rw-r--r--. 1 root root 2245 Oct 20 09:12 /etc/passwd
[student@fedora ~]$ head -3 /etc/passwd
root:x:0:0:Super User:/root:/bin/bash
bin:x:1:1:bin:/bin:/usr/sbin/nologin
daemon:x:2:2:daemon:/sbin:/usr/sbin/nologin
[student@fedora ~]$ grep student /etc/passwd
student:x:1000:1000:Student:/home/student:/bin/bash

FieldIn the exampleWhat it is
1studentthe user name, the one you log in with
2xthe password: x means that it is kept in /etc/shadow

41000the GID of the primary group
5Studentthe GECOS field: the full name, sometimes followed by the room and phone numbers, with ,

The . after the permissions, -rw-r--r--., means that the file has an SELinux label. You will see it on almost every file on Fedora: ignore it in this lab. Ubuntu does not show it.

getent​

/etc/passwd is not the only place where users can be kept: in a university or a company, the accounts are usually on a server in the network (LDAP, Active Directory, ...). That is why no program do not read /etc/passwd directly by themselves: they ask the C library, with getpwnam() (from a name to a user) and getpwuid() (from a UID to a user). The C library reads /etc/nsswitch.conf to find out where to look for the users, the passwords and the groups, and in which order. So ls, ps and id work the same way whether a user is kept in /etc/passwd or on a server.

[student@fedora ~]$ grep -E '^(passwd|shadow|group):' /etc/nsswitch.conf
passwd:     files systemd
shadow:     files
group:      files systemd

files means the files in /etc, systemd the users that systemd creates by itself (your system may also have sss, a network server). getent (get entries) asks the C library, exactly like ls and id do, so it finds a user wherever it is kept:

CommandFinds
getent passwd <NAME> or <UID>the user with this name, or this UID
getent passwdall the users
getent group <NAME> or <GID>the group with this name, or this GID
getent groupall the groups
sudo getent shadow <NAME>the line of the user from /etc/shadow, only for root
tip

When nothing is found, getent prints nothing, without an error.

[student@fedora ~]$ getent passwd 0
root:x:0:0:Super User:/root:/bin/bash
[student@fedora ~]$ getent passwd student
student:x:1000:1000:Student:/home/student:/bin/bash
[student@fedora ~]$ getent passwd nobody
nobody:x:65534:65534:Kernel Overflow User:/:/usr/sbin/nologin
tip

The output has the same format as /etc/passwd. Use getent instead of grep on /etc/passwd when you look for a user: grep root /etc/passwd also finds every line that has root somewhere else, for example in the home directory.

/etc/shadow​

[student@fedora ~]$ cat /etc/shadow

Hashes and Salt​

The password itself is never stored, only its hash: the result of a one-way function. It is easy to compute the hash of a password, but there is no way to compute the password from the hash: the only way back is to guess a password, hash it, and compare. The second field of /etc/shadow is made of parts separated by $:

PartIn the exampleWhat it is
algorithmythe hash function: y is yescrypt, 6 is SHA-512, 1 is the old MD5
parametersj9Tthe cost of the algorithm: how much work a hash takes
saltXr3aB7tPq2LkV9sD1fGh0Ja random text, different for every user, added to the password before hashing
hash9mQeT4bW1sZx...the hash of the salt and the password
note

To check a password, login (or sudo, or passwd) reads the algorithm, the parameters and the salt from /etc/shadow, hashes the typed password with them, and compares the result with the stored hash. If they are equal, the password is correct. openssl passwd computes a hash in the same way (-6 is SHA-512):

[student@fedora ~]$ openssl passwd -6 -salt Xr3aB7tP pass123

[student@fedora ~]$ openssl passwd -6 -salt Xr3aB7tP pass123

[student@fedora ~]$ openssl passwd -6 -salt Xr3aB7tP pass124
$6$Xr3aB7tP$msVqpr1xVM/DA2zRy9MVn8yIL5iisMXZpqd3XHD5Ix0aQ5QqD8D3Q91LXVy0w9hPqQLzRYsUVEH5g5oBfNp9//
[student@fedora ~]$ openssl passwd -6 -salt Lp0wQ2zM pass123
$6$Lp0wQ2zM$Uo9XUE/86KtNuRc.TcZpxeM0kWUejWZuFOaRQSujvsfACi8WRK55XpaV3Z3WE8TLEWQBF9Jgn4ByzOvO43Ukw0
  • The same password and the same salt always give the same hash: this is how the password is checked.
  • One different letter gives a completely different hash.
  • The same password with another salt gives another hash: two users with the same password have different lines in /etc/shadow.
info

Why is the hash not in /etc/passwd, which everyone can read? Because the check works for an attacker too: with a copy of the hash, they can hash one password after another, on their own computer, until one of them gives the same hash. Nobody sees these tries, and nothing slows them down, unlike login, which waits after a wrong password and writes it in the log. A slow algorithm, like yescrypt, makes every try cost more, and the salt makes the attacker start again for every user, but a simple password is still found quickly. That is why only root can read /etc/shadow: the programs that check passwords, login, sudo and passwd, run as root, so they can read it.

Changing a Password: passwd​

caution

When you type a password in the terminal, nothing appears on the screen. Type it anyway and press Enter. Fedora refuses passwords that are too short or too simple, unless you are root.

Groups​

A group is a set of users. A group has no rights by itself: a file can give permissions to a group, and sudo trusts one group, and then every member gets these rights. Like a user, a group has a name and a number, the GID (Group ID), and the kernel knows only the number. Every user has:

  • one primary group, the GID in /etc/passwd: the new files of the user get this group. On Fedora and Ubuntu, useradd creates a group with the same name as the user, only for them;
  • any number of supplementary groups, listed in /etc/group, for example wheel.

The local groups are kept in /etc/group, one group per line, with 4 fields:

[student@fedora ~]$ getent group wheel
wheel:x:10:student
[student@fedora ~]$ getent group student
student:x:1000:
FieldIn the exampleWhat it is
1wheelthe name of the group
2xthe password of the group, almost never used
310the GID
4studentthe members, separated by ,: the users that have it as a supplementary group
caution

The users that have a group as their primary group are not listed in its last field: student is the only member of the group student, but the list is empty. Use id <USER> to see all the groups of a user.

Logging In​

When you log in, a process gets the label of your user. On a text terminal, /dev/tty3 for example:

  1. systemd starts agetty on the terminal, as root; it prints login: and reads the user name;
  2. agetty becomes login (it runs exec), still as root, and it asks for the password;
  3. login finds the user with the C library, and checks the password with the hash from /etc/shadow;
  4. a child of login sets its GID, its groups and, at the end, its UID to the ones of the user; after that, it can never go back to root;
  5. the child changes to the home directory and runs (exec) the shell from /etc/passwd.

[student@fedora ~]$ ps -t tty3 -o user,pid,ppid,comm
USER         PID    PPID COMMAND
root        5120       1 login
student     5191    5120 bash

login still runs as root, and waits for the shell to end; the shell runs as student. Every program you start from it inherits this label. A graphical login and ssh do the same steps.

info

The groups are copied from the groups database only when a process gets the label of a user: at login, and by su and sudo. If you are added to a new group, the processes that are already running do not have it, and neither do their children: a new terminal window is a child of Sway, which got its groups when you logged in. To get the new group, log out and log in again, or, for one shell only, start a login shell with su - student, or run newgrp <GROUP>.

The root User​

root is the user with the UID 0. For a process whose effective UID is 0, the kernel skips most of its checks: it can read and write any file, send signals to any process, mount disks and change the network. Installing software and adding users need root for the same reason: they write files that belong to root, in /usr and in /etc. The home directory of root is /root, not /home/root, so that root can still log in when /home is on another disk that does not work.

The kernel looks only at the number: root is just the name of the UID 0, usually on the first line of /etc/passwd. Two user names with the same UID are the same user for the kernel: this is how an attacker can hide a second root.

danger

A mistake as root can destroy the whole system: root gets no Permission denied to stop it. Work as a regular user, and become root only for the commands that need it.

Becoming root: sudo and su​

sudo​

sudo runs one command as root. It asks for your password, not the one of root, and it lets you do it only if you are an administrator. A user is an administrator if they are a member of one special group, whose name depends on the distribution:

DistributionThe group of the administrators
Fedora, Red Hat, CentOSwheel
Ubuntu, Debian, Linux Mintsudo

To make a user an administrator, add them to this group; to take the right away, remove them from it (see Managing Users and Groups). student is in wheel, so it may use sudo:

[student@fedora ~]$ cat /etc/shadow
cat: /etc/shadow: Permission denied
[student@fedora ~]$ sudo whoami
[sudo] password for student:
root
[student@fedora ~]$ sudo whoami
root
  • sudo itself runs as root, and it starts the command as root too: whoami prints root.
  • It remembers the password for 5 minutes, in this terminal: the second sudo did not ask for it.
  • A user who is not an administrator gets bob is not in the sudoers file., and the command does not start.

sudo writes every command in the system log: who ran what, as whom, and from which directory.

[student@fedora ~]$ sudo journalctl -t sudo | tail -2
Oct 27 10:02:11 fedora sudo[3311]:  student : TTY=pts/0 ; PWD=/home/student ; USER=root ; COMMAND=/usr/bin/whoami
Oct 27 10:02:20 fedora sudo[3315]:  student : TTY=pts/0 ; PWD=/home/student ; USER=root ; COMMAND=/usr/bin/journalctl -t sudo

While the command runs, sudo does not go away: it waits for the command to end and passes on the signals that it receives. On Fedora, sudo also runs the command in a new pseudo terminal of its own (the option use_pty, see Terminal Emulators in lab 04), so there are two sudo processes: the first one stays on your terminal, the second one opens the new pseudo terminal and starts the command in it. With sudo sleep 300 running in a shell with the PID 2817:

[student@fedora ~]$ pstree -pu 2817
bash(2817)───sudo(3320,root)───sudo(3321)───sleep(3322)
[student@fedora ~]$ ps -o pid,ppid,tty,comm -p 3320,3321,3322
    PID    PPID TT       COMMAND
   3320    2817 pts/0    sudo
   3321    3320 pts/2    sudo
   3322    3321 pts/2    sleep
  • pstree -p shows the PIDs, and -u the user, where it changes: sudo runs as root, and so does everything under it.
  • The second sudo and sleep are on pts/2, not on pts/0: ps -t pts/0 does not show the command started with sudo. Find it with pstree, pgrep or the PPID instead.
info

The Redirect Trap​

sudo runs the command, not the whole line. The redirects are done by your shell, which runs as you, before sudo starts:

[student@fedora ~]$ sudo echo "192.168.1.20 printer" >> /etc/hosts
bash: /etc/hosts: Permission denied
[student@fedora ~]$ echo "192.168.1.20 printer" | sudo tee -a /etc/hosts
192.168.1.20 printer

  • In the first line, bash tries to open /etc/hosts for >>, as student, and fails: sudo echo never starts.
  • In the second line, tee runs as root: it reads the text from the pipe and writes it into the file and on the screen. -a (append) adds it at the end, like >>; without it, tee replaces the content of the file, like >.
tip

tee also prints the text on the screen. To hide it, send its output to /dev/null:

echo "192.168.1.20 printer" | sudo tee -a /etc/hosts > /dev/null. This redirect is also done by your shell, as you, but it works because of the permissions of /dev/null: they are rw-rw-rw- (666), so every user may write to it.

File Permissions​

Owner, Group and Permissions​

Every file and directory has one owner (a user), one group, and three sets of permissions: for the owner (u, user), for the group (g) and for all the others (o). The owner and the group are kept as numbers, a UID and a GID, and they are independent: the owner does not have to be a member of the group. ls -l shows them:

[student@fedora lab05]$ ls -l notes.txt
-rw-r-----. 1 student students 9 Oct 27 10:20 notes.txt

stat prints the same information, in the format you ask for:

-rw-r----- 640 student students notes.txt

%A are the permissions as letters, %a as a number (see chmod), %U the owner, %G the group and %n the name.

r, w and x​

The same letters have a different meaning for files and for directories:

PermissionValueFor a fileFor a directory

| x execute | 1 | run it as a program | enter it (cd) and reach the files inside, if you know their names |

A directory is a file whose content is a list of names, each pointing to a file. r reads this list, w changes it, and x uses it to reach a file. This has two consequences:

  • creating, renaming or deleting a file is a change of the directory, not of the file: with w on a directory you can delete a file that you cannot even read;
  • to reach a file, you need x on every directory of its path: cat /home/student/lab05/notes.txt needs x on /, /home, /home/student and /home/student/lab05.
[student@fedora lab05]$ ls -ld noread noenter

[student@fedora lab05]$ ls noread

top secret
[student@fedora lab05]$ ls noenter
ls: cannot access 'noenter/secret.txt': Permission denied
secret.txt
[student@fedora lab05]$ cd noenter
bash: cd: noenter: Permission denied
  • noread has x but no r: its names cannot be listed, but a file whose name you know can be opened.
  • noenter has r but no x: ls can read the names, but not reach the files to show them; cd cannot enter it.
info

On Fedora, the home directories are drwx------: the other users cannot even enter yours, so they cannot reach your files, whatever their permissions. On Ubuntu, they are drwxr-x---: the members of your primary group may also list and enter it, but this group usually has no other member. An older Ubuntu, or one upgraded from an older version, may still have drwxr-xr-x, open to everybody: check yours with ls -ld ~.

Which Permissions Apply?​

The kernel checks the label of the process in this order, and the first match decides:

  1. if the UID of the process is 0, root: everything is allowed (except running a file without any x);
  2. if the UID is the owner of the file: the u permissions are used;
  3. if one of the groups of the process is the group of the file: the g permissions are used;
  4. otherwise: the o permissions are used.

For notes.txt above, -rw-r----- student students:

Only one set is used. With ----rw----, the owner can do nothing, even if they are in the group: the owner already matched at step 2, so the g permissions are never checked.

umask​

New files do not get all the permissions: the program that creates them asks for rw-rw-rw- (666) for a file and rwxrwxrwx (777) for a directory, and the kernel removes the bits of the umask of the process. umask is a built-in command of the shell (help umask), and every process inherits it from its parent.

setuid​

passwd must write your new hash into /etc/shadow, which only root can change. /usr/bin/passwd belongs to root and has the setuid bit: whoever starts it, the process runs as root.

[student@fedora ~]$ ls -l /usr/bin/passwd /usr/bin/sudo /usr/bin/su
-rwsr-xr-x. 1 root root  32648 Jul 24 03:00 /usr/bin/passwd
-rwsr-xr-x. 1 root root  56920 Jul 24 03:00 /usr/bin/su
---s--x--x. 1 root root 262536 Jul 24 03:00 /usr/bin/sudo

When a program with the setuid bit starts, the kernel changes two of its credentials: the effective and the saved UID become the owner of the file, root. The real UID stays the one of the user who started it. Run passwd in one terminal (do not type anything), and look at it from another one:

[student@fedora ~]$ ps -o pid,ruser,euser,suser,comm -C passwd
    PID RUSER    EUSER    SUSER    COMMAND
   6011 student  root     root     passwd

The kernel checks the effective UID, so passwd may write /etc/shadow. passwd reads the real UID to find out who started it, so it changes only your password.

The Saved UID​

A careful setuid program does not work as root all the time: it works as you, and uses root only for the few steps that need it, so that a bug in the rest of it can only do what you could do anyway. The saved UID makes this possible. After the exec, the Uid: line of the program is 1000 0 0 0:

  1. the program sets its effective UID to its real one, 1000 (Uid: 1000 1000 0 1000): root stays only in the saved UID;
  2. when it needs root again, it sets its effective UID back to 0 (Uid: 1000 0 0 0): this is allowed, because 0 is its saved UID;
  3. when it does not need root any more, it sets all three UIDs to 1000 (Uid: 1000 1000 1000 1000): 0 is none of its UIDs now, so it can never go back.

danger

Never add +s to a program that belongs to root: it runs as root for everybody, and one bug in it makes anybody root. A setuid copy of bash gives a shell of root to every user. Leave the setuid bit to the programs that are made for it: passwd, su, sudo.

info

The kernel ignores the setuid and the setgid bit on scripts, like myid.sh. A script does not run by itself: the kernel starts the program on its first line, /bin/bash, and gives it the script to read. A bash with the label of root would be dangerous, because the user who starts it can change what it does, for example with environment variables. So the bits work only for compiled programs, like passwd.

setgid on a Directory​

When several users work in the same directory, the new files should belong to the group of the project, not to the primary group of each user. The setgid bit on a directory does this:

[student@fedora ~]$ sudo mkdir /srv/project
[student@fedora ~]$ sudo chgrp students /srv/project
[student@fedora ~]$ sudo chmod 2775 /srv/project
[student@fedora ~]$ ls -ld /srv/project

bob.txt belongs to bob, but its group is students, the group of the directory, not bob.

The Sticky Bit​

/tmp must be writable by everyone, so everyone has w on it. Without anything else, anyone could delete the files of the others. The sticky bit, t, allows deleting or renaming a file in the directory only to the owner of the file, the owner of the directory and root:

[student@fedora ~]$ ls -ld /tmp
drwxrwxrwt. 21 root root 520 Oct 27 10:00 /tmp
tip

find can look for the special bits: find /usr -perm -4000 prints the files that have at least the setuid bit.

    1. in the first terminal, start python3 as root; print its real, effective and saved UID;
    2. become student in the real and the effective UID, but keep root in the saved UID;
    3. take root back, in the effective UID only;
    4. set all three UIDs to 1000, and try to take root back once more.

    💡 In python3, import os first, then help(os.getresuid), help(os.setresuid) and help(os.seteuid); open('/etc/shadow').readline() reads the first line of a file; exit() leaves python3.

    Check: Uid: is 0 0 0 0, then 1000 1000 0 1000 and /etc/shadow is denied, then 1000 0 0 0 and it can be read again, because 0 was the saved UID; after the last step, Uid: is 1000 1000 1000 1000 and seteuid(0) fails with Operation not permitted. The 4th number, the file system UID, always follows the 2nd. → The Saved UID · Which Credentials Are Checked

    4. compare your PATH with the PATH that sudo gives to a command.

    💡 man sudo: search for shell and for preserve-env; printenv prints the value of one variable, and you can run it with sudo.

    Check: the first shell stays in ~/lab05, the login shell starts in /root; both have HOME=/root. By default, sudo removed COURSE; sudo also uses a PATH of its own, so a program from your ~/.local/bin is not found by sudo. → sudo · Environment Variables

  6. Shells inside shells: Follow the user of every process when you start shells inside shells, and see that not even root can log in as a system user.

    1. in the first terminal, print the PID of the shell;

    4. in the second terminal, show the tree of processes of the first shell, with the PIDs and the users, and print the real and effective user of every process in this tree, with ps;
    5. leave the shells one by one, and show the tree after each step.

    Check: even root gets This account is currently not available.: the shell of daemon is /usr/sbin/nologin, a program that prints this message and ends. The tree is bash───sudo───sudo───bash───su───bash: two sudo, because sudo runs the shell of root on a new pseudo terminal; pstree shows the user where it changes: sudo(...,root) and the last bash(...,bob); su runs as root, and its child as bob. Every exit removes the last shell. → su · /etc/passwd · Listing Processes

    1. as root, copy myid.sh to /srv/lab05/rootid.sh and give it 4755; run it;

    3. delete both copies right away.

    Check: the script prints student: the kernel ignores the setuid bit on scripts. rootsleep has the real UID 1000 and the effective UID 0: a setuid program of root runs as root for everybody.
