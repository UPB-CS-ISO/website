07. Software Development

In the sixth lab you processed text with filters and edited text files with vim and nano. In the programming course you write programs in C, and the IDE builds and runs them when you press a button. In this lab you will build them yourself, in the terminal, and see what happens behind that button. You will see how a compiled language differs from an interpreted one, compile with gcc, and follow the four steps of the compilation pipeline: the preprocessor, the compiler, the assembler and the linker. You will split a program into modules, read the build errors of each step, and set up an editor that shows these errors while you type, through the language server clangd. Then you will let make build the program for you, from a Makefile: rules, automatic variables, pattern rules, phony targets and header dependencies. At the end, you will stop a running program with the debugger gdb, and save the versions of your project with git.

The most important idea of this lab is that building a program is a chain of files: every file that you build (an object file, the executable) is made from other files (the sources, the headers, other object files) by one command. A Makefile writes this chain down as rules, and make compares the modification times of the files: it runs a command only when its result is missing, or older than one of the files it is made from.

Objectives​

  • Understand the difference between a compiled, an interpreted and a bytecode language
  • Compile and run a C program in the terminal with gcc, without an IDE, and turn on the warnings with -Wall
  • Follow the four steps of the compilation pipeline, and stop after each of them with gcc -E, -S and -c
  • Look inside the files of each step with file, nm and ldd
  • Split a program into modules (a .h and a .c file), compile every .c file to an object file, and link the object files into an executable
  • Read a build error, find out which step reported it, and fix it
  • Understand what a language server is and how an editor talks to it, and use clangd from an editor: errors, information, completion and go to definition
  • Write a Makefile with rules, and understand how make decides what to build from the modification times
  • Shorten a Makefile with automatic variables ($@, $<, $^), pattern rules and variables (CC, CFLAGS)
  • Add the phony targets all, run and clean, and declare them with .PHONY
  • Write the header dependencies on the right rules
  • Build a program with debug information (-g), stop it with gdb and look at its variables
  • Save the versions of a project with git init, git add, git commit, git status, git diff and git log

Compiling​

Compiled and Interpreted Languages​

The processor runs only machine code: instructions written as bytes, different for every family of processors (x86-64, ARM64, RISC-V). People write source code: text, in a programming language. Someone has to translate the source code into machine code, and the languages differ in who does it and when:

KindWho translates the source codeWhenExamples
compileda compiler, into machine code: the result is an executableonce, before the program runsC, C++, Rust, Go
interpretedan interpreter, a program that reads the source and does what it saysevery time the program runsshell scripts (bash, sh)
bytecodea compiler, into bytecode (machine code for an imaginary processor); a virtual machine runs itbefore the program runs (Java, C#), or when it starts (Python, JavaScript)Java, C#, Python, JavaScript

Think of a book in a foreign language: a compiled program is a printed translation, made once and read many times; an interpreted program is read with a translator next to you, who translates every sentence while you read.

[student@fedora lab07]$ ./hello.sh
Hello from bash!
[student@fedora lab07]$ file hello.sh /usr/bin/bash
hello.sh:      Bourne-Again shell script, ASCII text executable
/usr/bin/bash: ELF 64-bit LSB pie executable, x86-64, ...
  • hello.sh is text: the interpreter, bash, reads it line by line. bash itself is machine code, an ELF file (Executable and Linkable Format, the format of the programs on Linux), written in C and compiled.
CompiledInterpreted
speedfast: the processor runs the machine code directlyslower: the interpreter translates the source at every run
errorsthe compiler finds many of them before the program runsan error shows up only when its line runs
after a changecompile again, then runjust run it again

info

A language is not compiled or interpreted: the program that runs it is. python3 compiles a script to bytecode every time it starts, then its virtual machine runs the bytecode; only the modules that a script imports are kept compiled, in __pycache__. The virtual machines of Java and JavaScript also compile the code that runs often to machine code, while it runs: just in time (JIT).

Compiling a C Program: gcc​

gcc (the GNU Compiler Collection) is the C compiler of Linux, and often the one that runs behind the Build button of your IDE. The examples use hello.c, which exercise 1 creates in ~/lab07:

~/lab07/hello.c
#include <stdio.h>

#define TIMES 3

int main(void)
{
    // say hello a few times
    for (int i = 0; i < TIMES; i++) {
        printf("Hello, %d!\n", i);
    }
    return 0;
}
[student@fedora lab07]$ gcc hello.c -o hello
[student@fedora lab07]$ ./hello
Hello, 0!
Hello, 1!
Hello, 2!
  • gcc hello.c -o hello compiled hello.c into the executable hello; it printed nothing, because nothing went wrong. The program starts with ./: the current directory is not in PATH (see The PATH Search in lab 04).

The Compilation Pipeline​

gcc hello.c -o hello looks like one step, but it is four. Each step reads the file of the step before, and writes a new file. An option stops gcc after a step, so you can look at that file:

StepWhat it doesStop after itWrites
preprocessorcopies the #include files in, replaces the #defines, removes the commentsgcc -E hello.c -o hello.ihello.i, preprocessed C
compilertranslates C into assembly, the text form of the machine codegcc -S hello.chello.s, assembly
assemblertranslates assembly into machine codegcc -c hello.chello.o, object file
linkerjoins the object files and the libraries into an executablegcc hello.o -o hellohello, executable

Think of a car factory: the first station brings the parts together (the preprocessor), the next ones shape them (the compiler and the assembler), and the last one assembles the car (the linker).

The Preprocessor: gcc -E​

The lines that start with # are for the preprocessor. It changes the text before the compiler sees it, a bit like sed, and does not check that the result is correct C.

[student@fedora lab07]$ gcc -E hello.c -o hello.i
[student@fedora lab07]$ wc -l hello.c hello.i
   12 hello.c
  825 hello.i
  837 total
[student@fedora lab07]$ grep 'int printf' hello.i
extern int printf (const char *__restrict __format, ...);
[student@fedora lab07]$ tail -n 8 hello.i
int main(void)
{

    for (int i = 0; i < 3; i++) {
        printf("Hello, %d!\n", i);
    }
    return 0;
}
  • #include <stdio.h> copied the whole file /usr/include/stdio.h (and the files that it includes) into hello.i: hundreds of lines, among them the declaration of printf. The number of lines depends on the version of the C library.
  • #define TIMES 3 replaced TIMES with 3, and the comment is gone.

#include <stdio.h>, with angle brackets, looks only in the folders of the system, like /usr/include; #include "lib.h", with quotes, looks first in the folder of the .c file.

The Compiler: gcc -S​

The compiler translates C into assembly: one line for every instruction of the processor, still a text file.

[student@fedora lab07]$ gcc -S hello.c
[student@fedora lab07]$ grep -E 'call|cmpl|jle' hello.s
	call	printf@PLT
	cmpl	$2, -4(%rbp)
	jle	.L3
  • The loop became a compare (cmpl, is i at most 2?) and a jump back (jle, jump if less or equal).
  • printf is only called: its code is not in hello.s.

Two options make hello.s easier to read:

OptionWhat it does
-fverbose-asmwrites each line of C as a comment above its instructions, and the variable that each one uses
-masm=intelwrites the Intel syntax instead of the AT&T syntax, the default of gcc (x86 only)
[student@fedora lab07]$ gcc -S -fverbose-asm hello.c
[student@fedora lab07]$ grep -B1 cmpl hello.s
# hello.c:8:     for (int i = 0; i < TIMES; i++) {
	cmpl	$2, -4(%rbp)	#, i
[student@fedora lab07]$ gcc -S -masm=intel hello.c
[student@fedora lab07]$ grep -E 'call|cmp|jle' hello.s
	call	printf@PLT
	cmp	DWORD PTR -4[rbp], 2
	jle	.L3
  • -fverbose-asm showed that the compare comes from line 8 of hello.c, the for, and that -4(%rbp) is i.
  • -masm=intel wrote the same instructions in the Intel syntax, the one of the manuals of Intel and AMD and of most books: the operands are in the reverse order, without % and $, and the size is a word (DWORD PTR, 4 bytes) instead of a letter (the l of cmpl).

The Assembler: gcc -c​

The assembler translates the assembly into machine code. The result is an object file: machine code that cannot run yet, because it has holes. To call printf, the code needs its address, but printf is not defined in hello.c, so the assembler does not know where it is: it leaves an empty place, and a note with the name printf. The linker fills these holes later.

[student@fedora lab07]$ gcc -c hello.c
[student@fedora lab07]$ file hello.o
hello.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
[student@fedora lab07]$ nm hello.o
0000000000000000 T main
                 U printf
  • nm listed the names (the symbols) of hello.o: T means defined here (in the text, the code), U means used here but undefined.
  • objdump -d hello.o shows the machine code, as bytes, next to the assembly; -M intel uses the Intel syntax. To see each line of C above its machine code, compile with -g and add -S: gcc -g -c hello.c, then objdump -d -S -M intel hello.o.

The Linker​

The linker (ld, which gcc runs for you) joins the object files into an executable, and fills in their holes. For every name that an object file uses but does not define (a U in nm), the linker looks for the one place that defines it (a T), in another object file or in a library. If it finds none, it stops with undefined reference; if it finds two, with multiple definition (see Build Errors).

printf is defined in the C library, the file libc.so.6, which the linker searches for every program, without being asked. It is a shared library, so the linker does not copy printf into hello: it only writes down that hello needs libc.so.6.

[student@fedora lab07]$ gcc hello.o -o hello
[student@fedora lab07]$ file hello
hello: ELF 64-bit LSB pie executable, x86-64, ..., dynamically linked, ...
[student@fedora lab07]$ ldd hello
	linux-vdso.so.1 (0x00007ffc8d5f2000)
	libc.so.6 => /lib64/libc.so.6 (0x00007f2b6a200000)
	/lib64/ld-linux-x86-64.so.2 (0x00007f2b6a4b1000)
  • gcc saw an object file, not a .c file, so it ran only the linker.
  • ldd listed the libraries that hello needs when it starts: printf is not copied into hello, it stays in libc.so.6, which the system loads every time hello starts. The numbers in parentheses change at every run.

With gcc -static, the linker copies printf, and everything that it needs, from the C library into the executable: the program does not need libc.so.6 any more, but it is much larger. On Fedora, -static needs the package glibc-static. The exercises at home and the challenges build their own libraries: the details are in Libraries.

tip

gcc -save-temps hello.c -o hello runs the four steps and keeps the files of each step: hello.i, hello.s and hello.o.

Several Source Files​

A real program has many source files. Each part of the program, a module, is a pair of files:

FileWhat it hasWho uses itExample: lib
.h, the headerthe declarations: what the module offers, without the code; also its #defines and typesevery .c file that calls the module, with #includelib.h: int sum(int n);
.c, the sourcethe definitions: the code of the functionsthe compiler, which turns it into an object filelib.c: int sum(int n) { ... }

Every .c file that uses a module includes its header, so the compiler knows the name and the types of the functions it calls. The examples use the files of ~/lab07/project, a program that adds the numbers from 1 to MAX:

project/
├── main.c      # includes lib.h and print.h; main() calls sum() and print_result()
├── lib.h       # #define MAX 10, declares sum()
├── lib.c       # includes lib.h, defines sum()
├── print.h     # declares print_result()
└── print.c     # includes <stdio.h> and print.h, defines print_result() with printf()
~/lab07/project/lib.h
#ifndef LIB_H
#define LIB_H
#define MAX 10
int sum(int n);
#endif
  • #ifndef, #define and #endif are the include guard: if a .c file includes lib.h twice, the second copy is skipped.

Every .c file is compiled alone, to its own object file, and the linker joins the object files:

[student@fedora project]$ gcc -c main.c
[student@fedora project]$ gcc -c lib.c
[student@fedora project]$ gcc -c print.c
[student@fedora project]$ gcc main.o lib.o print.o -o app
[student@fedora project]$ ./app
sum = 55
  • In main.o, sum and print_result are U; the linker found them in lib.o and print.o.

This is why every .c file is compiled to its own object file. After a change to print.c, only print.o is out of date, so two commands are enough: gcc -c print.c compiles it again, and gcc main.o lib.o print.o -o app links the program.

gcc main.c lib.c print.c -o app gives the same program in one command, but it compiles all the files every time. With three files, this does not matter. The Linux kernel has more than 30 000 .c files: compiling only the ones that changed saves minutes at every build.

An Editor with a Language Server​

In the IDE of the programming course, the code is colored, names are completed and errors are marked while you type. In the terminal, two programs do this together: an editor, and a language server, a program that understands one language. For C, the language server is clangd.

The LSP (Language Server Protocol) is the common language between them: any editor that speaks LSP can use any language server. Without it, every editor needs its own plugin for every language.

Think of a colleague who reads over your shoulder while you write: the editor is your notebook, and the language server is the colleague, who reads every line and answers your questions about it.

How a Language Server Works​

When you open a C file, the editor starts clangd as a child process (lab 03) and talks to it through two pipes (lab 06), in short JSON messages. The editor sends the text after every change and asks questions; clangd answers them, and sends the errors by itself.

clangd checks the code while you type, like the compiler, but it does not build anything.

The Makefile​

After every change you must remember which commands to run again, and in which order. make does it for you. It reads a file named Makefile, from the current directory, that says, for every file to build, what it is made from and which commands make it. Then make runs only the commands that are needed.

Think of a recipe book in which each recipe lists its ingredients: to make a cake, you first make the cream it needs, but only if you do not already have fresh cream in the fridge.

A Rule​

A Makefile is a list of rules:

target: prerequisites
	command 1
	command 2
PartWhat it is
targetthe file to build
prerequisitesthe files it is made from, separated by spaces
recipethe commands that build it, one per line, each line starting with a TAB

The Makefile of hello has two rules:

~/lab07/Makefile
hello: hello.o
	gcc hello.o -o hello

hello.o: hello.c
	gcc -c hello.c
  • hello is linked from hello.o; hello.o is compiled from hello.c. make alone builds the first target, hello; make hello.o builds only hello.o.
caution

A TAB, not spaces

Every line of a recipe starts with a TAB character. With spaces, make stops with Makefile:2: *** missing separator. Stop. Most editors keep the TABs in a file named Makefile; in vim, :set list shows a TAB as ^I.

How make Decides​

To build a target, make:

  1. builds its prerequisites first, each with its own rule, in the same way;
  2. runs the recipe if the target does not exist, or if a prerequisite is newer than the target;
  3. otherwise, does nothing: the target is up to date.

A prerequisite without a rule, like hello.c, must exist. make compares only the modification times of the files (ls -l --full-time shows them, to the fraction of a second); it never reads the code.

[student@fedora lab07]$ make
gcc -c hello.c
gcc hello.o -o hello
[student@fedora lab07]$ make
make: 'hello' is up to date.
[student@fedora lab07]$ touch hello.c
[student@fedora lab07]$ make
gcc -c hello.c
gcc hello.o -o hello
  • The first make built both files: they did not exist. make prints every command before it runs it.
  • The second make did nothing: hello.c is older than hello.o, and hello.o is older than hello.
  • touch (see touch in lab 02) set the time of hello.c to now, as if you had edited it: hello.c became newer than hello.o, so make compiled it again, and then hello.o was newer than hello.

The picture shows the rule that make follows for every target, then the last make, step by step: make keeps a stack of the targets it is working on. It goes down to the prerequisites, then comes back up and runs the recipes that are needed.

CommandWhat it does

Automatic Variables​

Inside a recipe, make replaces the automatic variables with the names of the rule:

With them, the recipe of app is gcc $^ -o $@, and the recipes of the three object files become the same: gcc -c $< -o $@.

Pattern Rules​

A pattern rule is one rule for many files: % matches any name, the same one in the target and in the prerequisite. %.o: %.c means main.o: main.c, lib.o: lib.c, print.o: print.c, and any other object file.

app: main.o lib.o print.o
	gcc $^ -o $@

%.o: %.c
	gcc -c $< -o $@
  • 11 lines became 5. A new module needs only its object file in the list of app.

make also has built-in rules: without any rule for main.o, it still compiles main.c, with cc -c. Write your own rules, so that you choose the commands.

Phony Targets​

Some targets are not files: they are names for something that you ask make to do. clean deletes what make built:

clean:
	rm -f *.o app

make clean runs rm every time, because there is never a file named clean. But if one appears, clean has no prerequisites and the file exists, so it is up to date, and rm does not run:

[student@fedora project]$ touch clean
[student@fedora project]$ make clean
make: 'clean' is up to date.

The special target .PHONY lists the targets that are not files: make does not look for a file with their name, and always runs their recipes. The usual phony targets are:

Header Dependencies​

A header is also a prerequisite: an object file must be compiled again when a header that its .c file includes changes. With the Makefile above, make does not know that:

[student@fedora project]$ sed -i 's/MAX 10/MAX 100/' lib.h
[student@fedora project]$ make
make: Nothing to be done for 'all'.
[student@fedora project]$ ./app
sum = 55
  • The sum of the numbers from 1 to 100 is 5050, but main.o was not compiled again: lib.h is not in any rule.

The dependencies follow the #include lines. Look at the #include lines of every .c file, and add each header to the rule of its object file:

main.o: lib.h print.h
lib.o: lib.h
print.o: print.h
  • These rules have no recipe: they only add prerequisites, and the recipe still comes from %.o: %.c. Put them at the end of the Makefile, so that all stays the first target.
[student@fedora project]$ make
gcc -Wall -g -c main.c -o main.o
gcc -Wall -g -c lib.c -o lib.o
gcc main.o lib.o print.o -o app
[student@fedora project]$ ./app
sum = 5050
  • main.c and lib.c include lib.h: their object files were compiled again; print.o was kept.
caution

A header goes on the rule of an object file, never on the rule of the executable: with app: main.o lib.o print.o lib.h, make only links again the old main.o, which still has MAX equal to 10.

What clangd Needs to Know​

clangd checks each file as gcc would compile it, so it needs the same options, like -I <DIR>. Without them, a header from another folder gives '<HEADER>' file not found in the editor, even if make works. Give it the options in a file in the folder of the project:

Saving Versions: git​

Git is a version control system: it keeps the history of the files of a project. You can go back to any version, see what changed and why, and work on the same code together with other people. The folder with the files and their history (in the hidden folder .git) is a repository. A commit is a snapshot of all the files, with an author, a date and a message; its name is a hash, like ed6ba3b.

Think of the save points of a game: you save when things work, and you can always come back to a save point.

A change goes through three places on your computer: you edit the files, git add puts them in the staging area (what the next commit will have), and git commit saves the commit in the repository.

Working with GitHub​

The First Steps use only your computer; the exercises at home and the challenges also use GitHub.

A commit stays on your computer. A remote is a copy of the repository on a server, such as GitHub, GitLab or Codeberg: you push your commits to it, and pull from it the commits of your colleagues. A colleague starts by cloning the repository: a copy of the files and of the whole history, connected to the same remote, origin.

Think of a shared folder in the cloud that keeps every save point, with its author.

A pull request (PR) is a request, made on GitHub, to merge a branch into main. Your colleagues read the changes in the tab Files changed, comment on them, and press Merge pull request; then everybody runs git pull. The rule of most teams: do not commit on main directly; create a branch, push it, and open a pull request.

A library is a file with compiled functions, ready to be used by other programs: printf is in the C library, sqrt in the math library. There are two kinds:

By default, gcc links the C library as a shared library. -static copies it in:

[student@fedora lab07]$ gcc hello.c -o hello-dynamic
[student@fedora lab07]$ gcc -static hello.c -o hello-static
[student@fedora lab07]$ stat -c '%s %n' hello-dynamic hello-static
8880 hello-dynamic
650832 hello-static
[student@fedora lab07]$ ldd hello-static
	not a dynamic executable
  • The two programs come from the same source, with the same command; only -static differs. hello-static is about 70 times larger: it carries its own copy of printf, and of everything that printf needs. The sizes change from one system to another, and from one processor to another.
  • hello-static is still smaller than the C library (stat -L -c '%s' /lib64/libc.so.6 prints more than 1 MiB): the linker copied only the parts of the library that the program uses.

You can build your own libraries. -l<NAME> links lib<NAME>.so or, if there is none, lib<NAME>.a; it looks for them in the folders given with -L <DIR>, then in the folders of the system (/usr/lib64 on Fedora):
