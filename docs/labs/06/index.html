06. Text Processing

In the fifth lab you learned which user runs every program, and who may read and write every file. In this lab you will work with what is inside most of these files: text. You will meet the filters, small commands that read lines and write lines: cat, head, tail and sort work with whole lines, grep finds the lines that match a regular expression, cut, tr and sed change the inside of every line, and wc and awk count and compute. You will join them into pipelines that answer a question in one line, find out if a command worked from its exit code, and chain commands with && and ||. At the end, you will edit text files in the terminal with nano and vim, and try a newer editor, Helix (hx).

The most important idea of this lab is that text is the common language of the commands. Every filter reads lines of text, does one small thing with them, and writes lines of text, so the output of any filter can be the input of any other one. Pipes join filters into a pipeline: each command hands its text to the next one, a step closer to the answer, and the last one prints it. Besides its text, every command also gives back a number, its exit code, which tells the shell if it worked.

Objectives​

  • Understand what a filter is, and build a pipeline of filters that answers a question
  • Show, reverse and cut out lines with cat, tac, head and tail
  • Sort lines with sort, as text, as numbers and by a field, and count the repeated lines with uniq
  • Write regular expressions, basic and extended, and search with them with grep
  • Cut fields and characters out of every line with cut, and reverse or number the lines with rev and nl
  • Change, delete and squeeze characters with tr, and replace text with sed
  • Count lines, words and characters with wc, and compute sums and averages with awk
  • Find out if a command worked from its exit code, and chain commands with && and ||
  • Edit a text file in the terminal with nano and with vim and try hx

Filters​

A filter is a command that reads text, does one job with it, and writes the result to its standard output. It reads the files that it gets as parameters or, when it gets none, its standard input. In Pipes in lab 03 you joined a few of them with |: sort fruits.txt | uniq -c. A chain of commands joined by pipes is a pipeline.

Think of an assembly line in a factory: every worker does one small job on the piece, and passes it on. A filter does not know what is before it or after it: only its input and its output.

The filters of this lab do four kinds of jobs, and a typical pipeline uses them in this order:

KindWhat it doesCommands
line filterschooses which lines to keep, and their ordercat, tac, head, tail, sort, uniq
searchkeeps the lines that match a patterngrep
change textchanges what is inside every linecut, tr, sed, rev, nl
computeturns the lines into a count, a sum, ...wc, uniq -c, awk

[student@fedora lab06]$ grep ' 404$' access.log | cut -d' ' -f1 | sort | uniq -c
      2 10.0.0.3
      3 10.0.0.9
  • grep kept the lines that end with 404, the requests for pages that do not exist; cut kept only the first field, the address; sort | uniq -c counted every address. Each command is explained in the sections below.
tip

Build a pipeline one command at a time

Run the first command and look at its output. Then press ↑, add | and the next command, and look again: each step should bring the text a little closer to the answer. While you work, add | head at the end to see only the first lines of a long output, and remove it when you are done.

info

"Write programs that do one thing and do it well. Write programs to work together. Write programs to handle text streams, because that is a universal interface." (Doug McIlroy, the inventor of the Unix pipe)

All the commands of a pipeline run at the same time, each one in its own process, and the text flows between them while they run. The exercises at home and the challenges need the details: they are in How a Pipeline Runs.

Regular Expressions​

A regular expression (regex) is a pattern that describes some text. For example, c.l means "a c, then any character, then an l": it matches col in color and cal in call. Most programs that search text understand regular expressions: grep, sed and awk, the search with / in less, man and vim, and almost every programming language.

Think of a description of a person that you give to a friend at the station: you do not know the name, but "tall, with a red hat" finds the right person in the crowd. A regex finds the lines that match the description.

grep '<REGEX>' <FILE> prints the lines that contain a match of the regex. The examples use words.txt:

caution

A regex is not a glob

The * of a glob (see Globbing in lab 04) means "any characters"; in a regex, * means "the previous item, any number of times", and "any characters" is .*. Always put the regex between single quotes: without them, the shell may expand it as a glob, before grep starts. If the current directory has a file banana.txt, grep ba* fruits.txt becomes grep banana.txt fruits.txt.

With grep -E, five more characters are special: +, ?, { }, ( ) and |, and they make the regex shorter. The table also shows \b, which GNU grep understands with or without -E:

Changing Characters: tr​

tr (translate) changes single characters, not words. It reads only its standard input: give it a file with < or with a pipe.

  • tr : '\n' put every directory of PATH (lab 04) on its own line.

Replacing Text: sed​

sed (stream editor) changes the text as it passes through, like a worker on the assembly line: it reads a line, changes it, prints it, and goes on to the next one. The file itself does not change. Unlike tr, sed works with words and regular expressions, not with single characters. Its most used command is s (substitute), which replaces the text that a regex matches:

sed 's/<REGEX>/<NEW TEXT>/<FLAGS>' <FILE>
Written asWhat it does

s/apple/pear/greplaces every match of the line (global)
s/apple/pear/githe same, ignoring upper and lower case
sed -E 's/...//'the regex is an extended one, as for grep -E
s/apple//gthe new text is empty: deletes the matches
s|/usr|/opt|any character can separate the parts: useful when the text has /
[student@fedora lab06]$ echo 'apple and apple pie' | sed 's/apple/pear/'
pear and apple pie
[student@fedora lab06]$ echo 'apple and apple pie' | sed 's/apple/pear/g'
pear and pear pie
[student@fedora lab06]$ echo 'call 0722 123 456' | sed -E 's/[0-9]+/N/g'
call N N N
[student@fedora lab06]$ sed 's/,/ /g' students.csv
name age city
Alice 30 Paris
Bob 25 London
Carol 22 Bucharest
  • Without g, only the first apple changed.
  • [0-9]+ matched each number, and every match became N.
  • sed printed the changed text; students.csv itself did not change.
danger

sed -i writes the result back into the file, instead of printing it. There is no undo: run the command without -i first, and look at the output.

Computing: awk​

awk is a small programming language for tables. An awk program is a list of conditions, each with an action between { }: for every line, awk splits it into fields and runs the action of every condition that is true for the line. A condition is optional; END is a condition that is true once, after the last line.

Written asWhat it is
-F,the delimiter is ,; without -F, any run of spaces and tabs
$1, $2, ..., $NFthe fields; $NF is the last one, not to be confused with NF; $0 is the whole line
NF, NRthe number of fields of the line; the number of the line, from 1
==, !=, <, >=, ...compare two values: numbers as numbers, text as text; text goes between ": $2 == "apple"
~ /regex/, !~ /regex/matches, does not match a regex
&&, ||, !and, or, not
{ print $1, $3 }prints fields 1 and 3, separated by a space; print $1 $3, without the ,, prints alice3
{ s += $3; n++ }adds field 3 to the variable s, and adds 1 to n; variables start at 0

The examples use orders.csv, a header and 6 orders:

name,fruit,count
alice,apple,3
bob,kiwi,1
carol,apple,2
alice,banana,5
dan,apple,1
alice,apple,2
[student@fedora lab06]$ awk -F, '{ s += $3 } END { print s }' orders.csv
14
[student@fedora lab06]$ awk -F, 'NR > 1 { s += $3; n++ } END { print s / n }' orders.csv
2.33333
[student@fedora lab06]$ awk -F, '$2 == "apple" { s += $3 } END { print s }' orders.csv
8
[student@fedora lab06]$ awk -F, '$2 ~ /an/ { print $1, $2 }' orders.csv
alice banana
[student@fedora lab06]$ awk '{ print NF, $NF }' people.txt

3 London
  • The first program added field 3 of every line, and printed the sum at the end; the header count is not a number, so it added 0.
  • NR > 1 skipped the header, and n counted the orders: 14 / 6 = 2.33333.
  • $2 == "apple" added only the apples; $2 ~ /an/ printed the orders whose fruit contains an.
  • Without -F, awk split Bob 25 London at the run of spaces: 3 fields, no empty ones.
tip

Put the awk program between single quotes: $1 and $3 are for awk, not for the shell.

Exit Codes​

Every command ends with a number between 0 and 255, its exit code: 0 means success, any other number an error. The shell keeps the exit code of the last command in $? (see Special Parameters in lab 04). The manual page of a command says what its numbers mean, in the section EXIT STATUS:

grep ends withWhen

1it found nothing
2an error: for example, the file does not exist
[student@fedora lab06]$ grep -q kiwi fruits.txt
[student@fedora lab06]$ echo $?
0
[student@fedora lab06]$ grep -q mango fruits.txt
[student@fedora lab06]$ echo $?
1
[student@fedora lab06]$ grep kiwi nope.txt
grep: nope.txt: No such file or directory
[student@fedora lab06]$ echo $?
2
  • grep -q printed nothing; its exit code said if it found kiwi, 0, or not, 1.
CommandWhat it does
truenothing; it ends with 0
falsenothing; it ends with 1
exit <N>ends the shell, or a script, with the exit code N

A command killed by a signal (lab 04) ends with 128 plus the number of the signal: Ctrl+C (SIGINT, 2) gives 130.

Chaining Commands: && and ||​

Written asWhat it does
a ; bruns a, then b, whether a worked or not; like two separate lines
a && bruns b only if a ended with 0: "a, and then b"
a || bruns b only if a did not end with 0: "a, or else b"
[student@fedora lab06]$ grep -q kiwi fruits.txt && echo 'kiwi found'
kiwi found
[student@fedora lab06]$ grep -q mango fruits.txt && echo 'mango found'
[student@fedora lab06]$ grep -q mango fruits.txt || echo 'no mango'
no mango
[student@fedora lab06]$ mkdir -p backup && cp fruits.txt backup/ && echo 'saved'
saved
  • && skipped echo 'mango found', because grep ended with 1; || ran echo 'no mango' for the same reason.
  • cp ran only after mkdir worked, and echo only after cp worked.
caution

a && b || c is not "if a, then b, else c": the shell reads it from left to right, so c also runs when a works but b fails. It is safe when b cannot fail, like echo.

a && b || c is not "if a, then b, else c". The shell reads it from left to right, and || looks at the exit code of the last command that ran before it: when a works, that is b. So c also runs when a works but b fails: true && false || echo C prints C. You can use a && b || c as "if a, then b, else c" only when b cannot fail, like echo: then c runs only when a fails.

The Exit Code of a Pipeline​

The exit code of a pipeline is the exit code of its last command:

[student@fedora lab06]$ cut -d, -f2 orders.csv | grep -q kiwi && echo 'kiwi ordered' || echo 'no kiwi'
kiwi ordered
[student@fedora lab06]$ cut -d, -f2 nope.csv | sort
cut: nope.csv: No such file or directory
[student@fedora lab06]$ echo $?
0
  • In the first line, grep -q found kiwi in the column of the fruits: the pipeline ended with 0.
  • In the second, cut failed, but sort, the last command, worked: the pipeline ended with 0. The error message is on the screen, but $?, && and || see only the 0. How a Pipeline Runs shows how to catch the failure.

How a Pipeline Runs​

note

Going deeper

You do not need this section for the exercises of the lab, the 🧪 First Steps. Read it at home: the 🏠 Going Further exercises and the 📝 Challenges use it.

For a pipeline, the shell starts every command at the same time, each as a child process, and joins them with pipes. A pipe is a small buffer in the kernel: the output (1) of a command writes into it, and the input (0) of the next command reads from it. Think of a tube between two workers: the first one drops pieces in at one end, the second takes them out at the other.

What happensThe result
the pipe is empty, and the next command wants to readit waits until there is text
the pipe is full (64 KiB)the writer waits until the reader takes some text out
the writer endsthe reader gets the end of file, and can finish
the reader ends before the writerat its next write, the writer gets the signal SIGPIPE (13), and ends
Ctrl+C, Ctrl+Zthey go to all the commands: the pipeline is one job (lab 04)
[student@fedora lab06]$ yes | head -n 3
y
y
y
[student@fedora lab06]$ echo "${PIPESTATUS[@]}"
141 0
  • yes prints y without end; head ended after 3 lines, and yes got SIGPIPE at its next write: 128 + 13 = 141.
  • PIPESTATUS is a variable of bash with the exit codes of every command of the last pipeline; $? has only the last one.

The pipes of a process are in its directory in /proc (see The /proc File System in lab 03): readlink /proc/<PID>/fd/1 prints pipe:[48211] when output 1 goes to a pipe; both ends of the same pipe have the same number.

SettingWhat it does
set -o pipefailthe exit code of a pipeline is the one of the rightmost command that failed, or 0 if none failed; set +o pipefail turns it off
grep --line-bufferedgrep writes every line at once; without it, when its output is a pipe, it waits until it has 4 KiB of text
[student@fedora lab06]$ set -o pipefail
[student@fedora lab06]$ cut -d, -f2 nope.csv | sort
cut: nope.csv: No such file or directory
[student@fedora lab06]$ echo $?
1
[student@fedora lab06]$ set +o pipefail
  • With pipefail, the failure of cut was not hidden any more: the pipeline ended with 1.

Exit codes

  1. Predict the chain: Learn to read && and || without running the commands.

    First write down, on paper, what each line prints, then check:

    1. true && echo A || echo B

    2. false && echo A || echo B

    3. true || echo A && echo B

    4. false || false && echo C; echo $?

    5. true && false || echo D

      Check: A; B; B; nothing, then 1; D. The shell reads from left to right, and each && or || looks at the exit code of the last command that ran before it: in line 5, D is printed although the first command worked. → Chaining Commands

  2. What the numbers mean: Find out what the exit codes say, besides "success" and "error".

    1. find in the manual what ls means by 1 and by 2, and produce each of them;

    2. start sleep 100, end it with kill from another terminal, and print its exit code; do it again with kill -9;

    3. run bash -c 'exit 42' and print its exit code; then bash -c 'exit 300'.

      💡 man ls: search for Exit status; hide the long output of ls -R with > /dev/null 2>&1; kill -l 15 prints the name of signal 15; an exit code is one byte.

    Check: ls /nope ends with 2; ls -R /etc ends with 1, because some directories inside it cannot be read. kill gives 143 (128 + 15, SIGTERM), kill -9 gives 137 (128 + 9, SIGKILL). 42, then 44: 300 does not fit in one byte, and only 300 - 256 is kept. → Exit Codes · Signals

  3. A careful change: You must change kiwi into mango in orders.csv, directly in the file. Do it so that you can always go back.

    1. with one line: copy orders.csv to orders.bak; only if the copy worked, change the file with sed -i; print changed if both worked, or not changed otherwise;
    2. check the content of both files;
    3. run the same line again, but copy into /nope/orders.bak;
    4. put the original orders.csv back, from orders.bak.

    💡 Replacing Text: sed and Chaining Commands.

    Check: after step 1, orders.csv has bob,mango,1 and orders.bak has bob,kiwi,1. In step 3, cp fails, sed does not run, and not changed is printed. At the end, grep -c kiwi orders.csv prints 1. → Chaining Commands · Replacing Text: sed

How a pipeline runs

  1. The processes of a pipeline: See that the commands of a pipeline run together, as one job.

    1. in the second terminal, print the PID of the shell, then run sleep 300 | sleep 301 | cat;
    2. in the first terminal, show the tree of processes of the second shell, with the PIDs; list these processes with their PID, PPID, process group, state and name;
    3. stop the pipeline with Ctrl+Z, and list them again; continue it with fg, and end it with Ctrl+C.

    💡 man pstree: search for pid; man ps: search for pgid and for state.

    Check: the three commands are children of the same bash, started at the same time, and they have the same process group: the PID of the first sleep. They are all S (waiting); after Ctrl+Z, all T (stopped); Ctrl+C ends all three. → How a Pipeline Runs · Foreground and Background

  2. Follow the pipe: Find the pipe between two commands in /proc.

    1. in the second terminal, run sleep 300 | cat;
    2. in the first terminal, find the PIDs of sleep and cat, and print where the inputs (0) and the outputs (1) of both lead;
    3. end the pipeline.

    💡 man pgrep; man readlink; the file descriptors of a process are in /proc/<PID>/fd (lab 03).

    Check: the output of sleep and the input of cat are the same pipe:[...], with the same number; the input of sleep and the output of cat are the terminal, /dev/pts/.... → How a Pipeline Runs · The /proc File System

  3. Who ends first: Find out what happens to a command whose reader stopped reading.

    For each line, first guess the exit codes of the two commands, then print them with PIPESTATUS:

    1. yes | head -n 3;
    2. seq 5 | sleep 2;
    3. seq 100000 | sleep 2.

    💡 kill -l 13; seq 100000 | wc -c tells how much text seq writes; the pipe holds 64 KiB.

    Check: 141 0: yes got SIGPIPE. 0 0: the 5 short lines fit in the pipe, and seq ended before sleep. 141 0: about 575 KiB do not fit, so seq waited for a reader; when sleep ended without reading, seq got SIGPIPE. → How a Pipeline Runs

  4. A failure in the middle: Every night, a pipeline counts the customers of the shop. One night the file was missing, and the report said 0, with no error. Make the pipeline tell the truth.

    1. run cut -d, -f1 nope.csv | sort -u | wc -l; then, with one echo, print its exit code and the exit codes of every command;

    2. add && echo ok || echo failed after the pipeline;

    3. turn on pipefail, and run step 2 again; then turn it off.

      💡 How a Pipeline Runs; echo is a command too: after it, $? and PIPESTATUS describe the echo, not the pipeline.

    Check: the pipeline prints 0 and ends with 0, but PIPESTATUS is 1 0 0; without pipefail it says ok, with pipefail it says failed. → How a Pipeline Runs · The Exit Code of a Pipeline

  5. Watch a live log: Watch the requests that end with 404 while they arrive, and only their addresses.

    1. in the second terminal, follow live.log and keep only the lines that contain 404;
    2. in the first terminal, add the line 10.0.0.9 GET /x 404 to live.log, then the line 10.0.0.7 GET / 200;
    3. in the second terminal, add cut at the end, to keep only the address; add another 404 line;
    4. fix the pipeline of step 3, so that the address appears right away.

    💡 How a Pipeline Runs; man grep: search for line-buffered.

    Check: in step 2 only the 404 line appears, right away. In step 3 nothing appears: the output of grep goes into a pipe now, and grep waits until it has 4 KiB of text. With grep --line-buffered, the address appears at once. → How a Pipeline Runs · The First and the Last Lines
