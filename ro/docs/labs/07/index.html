07. Dezvoltarea aplicațiilor

În laboratorul 6 ați prelucrat text cu filtre și ați editat fișiere text cu vim și nano. La cursul de programare scrieți programe în C, iar IDE-ul le compilează și le rulează când apăsați un buton. În acest laborator le compilați singuri, în terminal, și vedeți ce se întâmplă în spatele acelui buton. Aflați prin ce diferă un limbaj compilat de unul interpretat, compilați cu gcc și urmăriți cele patru etape ale compilării: preprocesorul, compilatorul, asamblorul și linkerul. Împărțiți un program în module, citiți erorile de compilare din fiecare etapă și configurați un editor care vă arată aceste erori chiar în timp ce scrieți, cu ajutorul serverului de limbaj clangd. Apoi îl lăsați pe make să compileze programul în locul vostru, pe baza unui Makefile: reguli, variabile automate, reguli cu șablon, ținte false și dependențe de headere. La final, opriți un program în timp ce rulează cu debuggerul gdb și salvați versiunile proiectului cu git.

Cea mai importantă idee a laboratorului este că un program se construiește printr-un lanț de fișiere: fiecare fișier construit (un fișier obiect, executabilul) se obține din alte fișiere (sursele, headerele, alte fișiere obiect) printr-o singură comandă. Un Makefile descrie acest lanț sub formă de reguli, iar make compară timpii de modificare ai fișierelor: rulează o comandă doar dacă rezultatul ei lipsește sau este mai vechi decât unul dintre fișierele din care se obține.

Obiective​

  • Să înțelegeți diferența dintre un limbaj compilat, unul interpretat și unul bazat pe bytecode
  • Să compilați și să rulați un program C în terminal cu gcc, fără IDE, și să activați avertismentele cu -Wall
  • Să urmăriți cele patru etape ale compilării și să vă opriți după fiecare dintre ele cu gcc -E, -S și -c
  • Să vă uitați în fișierele produse de fiecare etapă cu file, nm și ldd
  • Să împărțiți un program în module (un fișier .h și unul .c), să compilați fiecare fișier .c într-un fișier obiect și să legați fișierele obiect într-un executabil
  • Să citiți o eroare de compilare, să aflați ce etapă a raportat-o și să o corectați
  • Să înțelegeți ce este un server de limbaj și cum comunică editorul cu el, și să folosiți clangd dintr-un editor: erori, informații, completare și salt la definiție
  • Să scrieți un Makefile cu reguli și să înțelegeți cum decide make ce construiește, pe baza timpilor de modificare
  • Să scurtați un Makefile cu variabile automate ($@, $<, $^), reguli cu șablon și variabile (CC, CFLAGS)
  • Să adăugați țintele false all, run și clean și să le declarați cu .PHONY
  • Să scrieți dependențele de headere pe regulile potrivite
  • Să compilați un program cu informații de depanare (-g), să îl opriți cu gdb și să vă uitați la variabilele lui
  • Să salvați versiunile unui proiect cu git init, git add, git commit, git status, git diff și git log

Compilarea​

Limbaje compilate și limbaje interpretate​

Procesorul rulează doar cod mașină: instrucțiuni scrise ca octeți, diferite pentru fiecare familie de procesoare (x86-64, ARM64, RISC-V). Oamenii scriu cod sursă: text, într-un limbaj de programare. Cineva trebuie să traducă codul sursă în cod mașină, iar limbajele diferă prin cine face traducerea și când:

TipCine traduce codul sursăCândExemple
compilatun compilator, în cod mașină: rezultatul este un executabilo singură dată, înainte să ruleze programulC, C++, Rust, Go
interpretatun interpretor, un program care citește sursa și face ce scrie în eala fiecare rulare a programuluiscripturi shell (bash, sh)
bytecodeun compilator, în bytecode (cod mașină pentru un procesor imaginar); o mașină virtuală îl ruleazăînainte să ruleze programul (Java, C#) sau când pornește (Python, JavaScript)Java, C#, Python, JavaScript

Gândiți-vă la o carte într-o limbă străină: un program compilat este o traducere tipărită, făcută o dată și citită de multe ori; un program interpretat se citește cu un traducător alături, care traduce fiecare frază pe măsură ce citiți.

[student@fedora lab07]$ ./hello.sh
Hello from bash!
[student@fedora lab07]$ file hello.sh /usr/bin/bash
hello.sh:      Bourne-Again shell script, ASCII text executable
/usr/bin/bash: ELF 64-bit LSB pie executable, x86-64, ...
  • hello.sh este text: interpretorul, bash, îl citește linie cu linie. bash însuși este cod mașină, un fișier ELF (Executable and Linkable Format, formatul programelor în Linux), scris în C și compilat.

Nu limbajul este compilat sau interpretat, ci programul care îl rulează. python3 compilează un script în bytecode la fiecare pornire, apoi mașina lui virtuală rulează bytecode-ul; doar modulele importate de script se păstrează compilate, în __pycache__. Mașinile virtuale pentru Java și JavaScript compilează în plus în cod mașină codul care rulează des, chiar în timpul rulării: just in time (JIT).

Compilarea unui program C: gcc​

gcc (GNU Compiler Collection) este compilatorul de C din Linux și, de multe ori, cel care rulează în spatele butonului Build din IDE. Exemplele folosesc hello.c, pe care îl creează exercițiul 1 în ~/lab07:

~/lab07/hello.c
#include <stdio.h>

#define TIMES 3

int main(void)
{
    // say hello a few times
    for (int i = 0; i < TIMES; i++) {
        printf("Hello, %d!\n", i);
    }
    return 0;
}
[student@fedora lab07]$ gcc hello.c -o hello
[student@fedora lab07]$ ./hello
Hello, 0!
Hello, 1!
Hello, 2!
  • gcc hello.c -o hello a compilat hello.c în executabilul hello; nu a afișat nimic, pentru că nu a apărut nicio problemă. Programul se pornește cu ./, deoarece directorul curent nu este în PATH (vedeți Căutarea în PATH din laboratorul 4).

În spatele butonului din IDE

Butonul Build al unui IDE (Code::Blocks, Visual Studio Code, CLion) rulează gcc cu opțiuni ca acestea, iar Run pornește executabilul; jurnalul de compilare al IDE-ului arată comenzile exacte. În terminal nu există niciun buton care să compileze programul înainte de rulare: după ce modificați un fișier .c, rulați voi gcc (sau make).

Fișierele C le scrieți cu unul dintre editoarele din Editoare de text, din laboratorul 6; după Erori de compilare, configurați unul care înțelege C.

Etapele compilării​

gcc hello.c -o hello pare un singur pas, dar de fapt sunt patru. Fiecare etapă citește fișierul produs de etapa anterioară și scrie un fișier nou. Cu o opțiune, gcc se oprește după o anumită etapă, ca să vă puteți uita la fișierul respectiv:

EtapăCe faceOprire după eaScrie
preprocesorcopiază fișierele din #include, înlocuiește #define-urile, elimină comentariilegcc -E hello.c -o hello.ihello.i, C preprocesat
compilatortraduce C în limbaj de asamblare, forma text a codului mașinăgcc -S hello.chello.s, cod în limbaj de asamblare
asamblortraduce limbajul de asamblare în cod mașinăgcc -c hello.chello.o, fișier obiect
linkerunește fișierele obiect și bibliotecile într-un executabilgcc hello.o -o hellohello, executabil

Gândiți-vă la o fabrică de mașini: prima stație aduce piesele la un loc (preprocesorul), următoarele le dau formă (compilatorul și asamblorul), iar ultima asamblează mașina (linkerul).

Preprocesorul: gcc -E​

Liniile care încep cu # sunt pentru preprocesor. Acesta modifică textul înainte să-l vadă compilatorul, cam ca sed, și nu verifică dacă rezultatul este cod C corect.

[student@fedora lab07]$ gcc -E hello.c -o hello.i
[student@fedora lab07]$ wc -l hello.c hello.i
   12 hello.c
  825 hello.i
  837 total
[student@fedora lab07]$ grep 'int printf' hello.i
extern int printf (const char *__restrict __format, ...);
[student@fedora lab07]$ tail -n 8 hello.i
int main(void)
{

    for (int i = 0; i < 3; i++) {
        printf("Hello, %d!\n", i);
    }
    return 0;
}
  • #include <stdio.h> a copiat în hello.i tot fișierul /usr/include/stdio.h (și fișierele incluse de el): sute de linii, printre care și declarația lui printf. Numărul de linii depinde de versiunea bibliotecii C.
  • #define TIMES 3 a înlocuit TIMES cu 3, iar comentariul a dispărut.

#include <stdio.h>, cu paranteze unghiulare, caută doar în directoarele sistemului, precum /usr/include; #include "lib.h", cu ghilimele, caută mai întâi în directorul fișierului .c.

Compilatorul: gcc -S​

Compilatorul traduce C în limbaj de asamblare: câte o linie pentru fiecare instrucțiune a procesorului, tot într-un fișier text.

[student@fedora lab07]$ gcc -S hello.c
[student@fedora lab07]$ grep -E 'call|cmpl|jle' hello.s
	call	printf@PLT
	cmpl	$2, -4(%rbp)
	jle	.L3
  • Bucla a devenit o comparație (cmpl: este i cel mult 2?) și un salt înapoi (jle, jump if less or equal).
  • printf este doar apelat: codul lui nu se află în hello.s.

Două opțiuni fac hello.s mai ușor de citit:

OpțiuneCe face
-fverbose-asmscrie fiecare linie de C ca un comentariu deasupra instrucțiunilor ei și variabila pe care o folosește fiecare
-masm=intelscrie sintaxa Intel în loc de sintaxa AT&T, cea implicită pentru gcc (doar pe x86)
[student@fedora lab07]$ gcc -S -fverbose-asm hello.c
[student@fedora lab07]$ grep -B1 cmpl hello.s
# hello.c:8:     for (int i = 0; i < TIMES; i++) {
	cmpl	$2, -4(%rbp)	#, i
[student@fedora lab07]$ gcc -S -masm=intel hello.c
[student@fedora lab07]$ grep -E 'call|cmp|jle' hello.s
	call	printf@PLT
	cmp	DWORD PTR -4[rbp], 2
	jle	.L3
  • -fverbose-asm a arătat că comparația vine de la linia 8 din hello.c, for-ul, și că -4(%rbp) este i.
  • -masm=intel a scris aceleași instrucțiuni în sintaxa Intel, cea din manualele Intel și AMD și din majoritatea cărților: operanzii sunt în ordine inversă, fără % și $, iar dimensiunea este un cuvânt (DWORD PTR, 4 octeți) în loc de o literă (l din cmpl).

Asamblorul: gcc -c​

Asamblorul traduce limbajul de asamblare în cod mașină. Rezultatul este un fișier obiect: cod mașină care încă nu poate rula, pentru că are goluri. Ca să apeleze printf, codul are nevoie de adresa funcției, dar printf nu este definit în hello.c, deci asamblorul nu știe unde se află: lasă un loc gol și o notă cu numele printf. Linkerul umple mai târziu aceste goluri.

[student@fedora lab07]$ gcc -c hello.c
[student@fedora lab07]$ file hello.o
hello.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
[student@fedora lab07]$ nm hello.o
0000000000000000 T main
                 U printf
  • nm a listat numele (simbolurile) din hello.o: T înseamnă definit aici (în text, adică în cod), iar U înseamnă folosit aici, dar nedefinit (undefined).
  • objdump -d hello.o afișează codul mașină, ca octeți, alături de limbajul de asamblare; -M intel folosește sintaxa Intel. Ca să vedeți fiecare linie de C deasupra codului ei mașină, compilați cu -g și adăugați -S: gcc -g -c hello.c, apoi objdump -d -S -M intel hello.o.

Linkerul​

Linkerul (ld, pe care îl rulează gcc pentru voi) unește fișierele obiect într-un executabil și le umple golurile. Pentru fiecare nume pe care un fișier obiect îl folosește, dar nu îl definește (un U în nm), linkerul caută singurul loc care îl definește (un T), într-un alt fișier obiect sau într-o bibliotecă. Dacă nu găsește niciunul, se oprește cu undefined reference; dacă găsește două, cu multiple definition (vedeți Erori de compilare).

printf este definit în biblioteca C, fișierul libc.so.6, în care linkerul caută pentru orice program, fără să i se ceară. Este o bibliotecă partajată, așa că linkerul nu copiază printf în hello: doar notează că hello are nevoie de libc.so.6.

[student@fedora lab07]$ gcc hello.o -o hello
[student@fedora lab07]$ file hello
hello: ELF 64-bit LSB pie executable, x86-64, ..., dynamically linked, ...
[student@fedora lab07]$ ldd hello
	linux-vdso.so.1 (0x00007ffc8d5f2000)
	libc.so.6 => /lib64/libc.so.6 (0x00007f2b6a200000)
	/lib64/ld-linux-x86-64.so.2 (0x00007f2b6a4b1000)
  • gcc a primit un fișier obiect, nu un fișier .c, așa că a rulat doar linkerul.
  • ldd a listat bibliotecile de care are nevoie hello când pornește: printf nu este copiat în hello, ci rămâne în libc.so.6, pe care sistemul o încarcă la fiecare pornire a lui hello. Numerele din paranteze se schimbă la fiecare rulare.

Cu gcc -static, linkerul copiază printf, împreună cu tot ce îi trebuie, din biblioteca C în executabil: programul nu mai are nevoie de libc.so.6, dar este mult mai mare. Pe Fedora, -static are nevoie de pachetul glibc-static. Exercițiile pentru acasă și provocările își construiesc propriile biblioteci: detaliile sunt în Biblioteci.

Mai multe fișiere sursă​

Un program real are multe fișiere sursă. Fiecare parte a programului, un modul, este o pereche de fișiere:

FișierCe conțineCine îl foloseșteExemplu: lib
.h, headeruldeclarațiile: ce oferă modulul, fără cod; plus #define-urile și tipurile luifiecare fișier .c care apelează modulul, cu #includelib.h: int sum(int n);
.c, sursadefinițiile: codul funcțiilorcompilatorul, care îl transformă într-un fișier obiectlib.c: int sum(int n) { ... }

Fiecare fișier .c care folosește un modul include headerul acestuia, ca să știe compilatorul numele și tipurile funcțiilor apelate. Exemplele folosesc fișierele din ~/lab07/project, un program care adună numerele de la 1 la MAX:

project/
├── main.c      # include lib.h și print.h; main() apelează sum() și print_result()
├── lib.h       # #define MAX 10, declară sum()
├── lib.c       # include lib.h, definește sum()
├── print.h     # declară print_result()
└── print.c     # include <stdio.h> și print.h, definește print_result() cu printf()
~/lab07/project/lib.h
#ifndef LIB_H
#define LIB_H
#define MAX 10
int sum(int n);
#endif
  • #ifndef, #define și #endif formează garda de includere (include guard): dacă un fișier .c include lib.h de două ori, a doua copie este sărită.

Fiecare fișier .c se compilează separat, în propriul fișier obiect, iar linkerul unește fișierele obiect:

[student@fedora project]$ gcc -c main.c
[student@fedora project]$ gcc -c lib.c
[student@fedora project]$ gcc -c print.c
[student@fedora project]$ gcc main.o lib.o print.o -o app
[student@fedora project]$ ./app
sum = 55
  • În main.o, sum și print_result sunt U; linkerul le-a găsit în lib.o și în print.o.

De aceea fiecare fișier .c se compilează în propriul fișier obiect. După o modificare în print.c, doar print.o este depășit, deci ajung două comenzi: gcc -c print.c îl compilează din nou, iar gcc main.o lib.o print.o -o app leagă programul.

gcc main.c lib.c print.c -o app produce același program dintr-o singură comandă, dar compilează toate fișierele de fiecare dată. Cu trei fișiere, nu contează. Nucleul Linux are însă peste 30 000 de fișiere .c: dacă le compilați doar pe cele modificate, câștigați minute întregi la fiecare compilare.

Un editor cu server de limbaj​

În IDE-ul de la cursul de programare, codul este colorat, numele se completează singure, iar erorile sunt marcate în timp ce scrieți. În terminal, de lucrul acesta se ocupă împreună două programe: un editor și un server de limbaj (language server), un program care înțelege un singur limbaj. Pentru C, serverul de limbaj este clangd.

LSP (Language Server Protocol) este limba comună a celor două: orice editor care vorbește LSP poate folosi orice server de limbaj. Fără el, fiecare editor ar avea nevoie de câte un plugin pentru fiecare limbaj.

Gândiți-vă la un coleg care se uită peste umărul vostru în timp ce scrieți: editorul este caietul, iar serverul de limbaj este colegul, care citește fiecare linie și vă răspunde la întrebări despre ea.

Cum funcționează un server de limbaj​

Când deschideți un fișier C, editorul pornește clangd ca proces copil (laboratorul 3) și comunică cu el prin două pipe-uri (laboratorul 6), în mesaje JSON scurte. Editorul trimite textul după fiecare modificare și pune întrebări; clangd răspunde la ele și trimite din proprie inițiativă erorile găsite.

clangd verifică codul în timp ce scrieți, la fel ca un compilator, dar nu construiește nimic.

Makefile-ul​

După fiecare modificare trebuie să țineți minte ce comenzi rulați din nou și în ce ordine. make face asta în locul vostru. Citește din directorul curent un fișier numit Makefile, care spune, pentru fiecare fișier de construit, din ce se obține și ce comenzi îl produc. Apoi make rulează doar comenzile necesare.

Gândiți-vă la o carte de rețete în care fiecare rețetă își listează ingredientele: ca să faceți un tort, pregătiți mai întâi crema de care are nevoie, dar numai dacă nu aveți deja cremă proaspătă în frigider.

O regulă​

Un Makefile este o listă de reguli:

target: prerequisites
	command 1
	command 2
ParteCe este
ținta (target)fișierul de construit
dependențele (prerequisites)fișierele din care se obține, separate prin spații
rețeta (recipe)comenzile care îl construiesc, câte una pe linie, fiecare linie începând cu un TAB

Makefile-ul pentru hello are două reguli:

~/lab07/Makefile
hello: hello.o
	gcc hello.o -o hello

hello.o: hello.c
	gcc -c hello.c
  • hello se obține legând hello.o; hello.o se obține compilând hello.c. make fără parametri construiește prima țintă, hello; make hello.o construiește doar hello.o.
atenție

Un TAB, nu spații

Fiecare linie a unei rețete începe cu un caracter TAB. Cu spații, make se oprește cu Makefile:2: *** missing separator. Stop. Majoritatea editoarelor păstrează TAB-urile într-un fișier numit Makefile; în vim, :set list afișează un TAB ca ^I.

Cum decide make​

Ca să construiască o țintă, make:

  1. construiește mai întâi dependențele ei, fiecare cu propria regulă, în același fel;
  2. rulează rețeta dacă ținta nu există sau dacă o dependență este mai nouă decât ținta;
  3. altfel nu face nimic: ținta este la zi (up to date).

O dependență fără regulă, precum hello.c, trebuie să existe. make compară doar timpii de modificare ai fișierelor (ls -l --full-time îi afișează, până la fracțiuni de secundă); nu citește niciodată codul.

[student@fedora lab07]$ make
gcc -c hello.c
gcc hello.o -o hello
[student@fedora lab07]$ make
make: 'hello' is up to date.
[student@fedora lab07]$ touch hello.c
[student@fedora lab07]$ make
gcc -c hello.c
gcc hello.o -o hello
  • Primul make a construit ambele fișiere, pentru că nu existau. make afișează fiecare comandă înainte să o ruleze.
  • Al doilea make nu a făcut nimic: hello.c este mai vechi decât hello.o, iar hello.o este mai vechi decât hello.
  • touch (vedeți touch din laboratorul 2) a setat timpul lui hello.c la momentul curent, ca și cum l-ați fi editat: hello.c a devenit mai nou decât hello.o, așa că make l-a compilat din nou, iar apoi hello.o a fost mai nou decât hello.

Figura arată regula pe care o urmează make pentru fiecare țintă, apoi ultimul make, pas cu pas: make ține o stivă cu țintele la care lucrează. Coboară până la dependențe, apoi urcă înapoi și rulează rețetele necesare.

ComandăCe face
makeconstruiește prima țintă din Makefile și doar ce nu este la zi
make <TARGET>construiește <TARGET>
make -nafișează comenzile pe care le-ar rula, fără să le ruleze (dry run, rulare de probă)
make -Bconstruiește din nou toate țintele, chiar și pe cele care sunt la zi
make <VAR>=<VALUE>schimbă o variabilă doar pentru această rulare; Makefile-ul rămâne la fel (vedeți Variabile)
make -C <DIR>intră mai întâi în <DIR> și lucrează acolo, ca și cum ați fi rulat make în <DIR>
make --debug=vexplică de ce construiește sau sare peste fiecare țintă
make -j<N>rulează până la <N> comenzi în același timp

Un Makefile pentru un proiect​

Pentru proiect, fiecare fișier obiect are o regulă, iar app se obține legând cele trei fișiere obiect:

~/lab07/project/Makefile
app: main.o lib.o print.o
	gcc main.o lib.o print.o -o app

main.o: main.c
	gcc -c main.c

lib.o: lib.c
	gcc -c lib.c

print.o: print.c
	gcc -c print.c
[student@fedora project]$ make
gcc -c main.c
gcc -c lib.c
gcc -c print.c
gcc main.o lib.o print.o -o app
[student@fedora project]$ touch print.c
[student@fedora project]$ make
gcc -c print.c
gcc main.o lib.o print.o -o app
  • După touch print.c, main.o și lib.o erau încă la zi: make a compilat doar print.c, apoi a legat programul.

Cele trei reguli pentru fișierele obiect sunt aproape identice. Următoarele trei secțiuni scurtează Makefile-ul.

Variabile automate​

Într-o rețetă, make înlocuiește variabilele automate cu numele din regulă:

VariabilăCe înseamnăÎn regula app: main.o lib.o print.o
$@țintaapp
$<prima dependențămain.o
$^toate dependențelemain.o lib.o print.o

Cu ele, rețeta lui app devine gcc $^ -o $@, iar rețetele celor trei fișiere obiect devin identice: gcc -c $< -o $@.

Reguli cu șablon​

O regulă cu șablon (pattern rule) este o singură regulă pentru mai multe fișiere: % se potrivește cu orice nume, același în țintă și în dependență. %.o: %.c înseamnă main.o: main.c, lib.o: lib.c, print.o: print.c și orice alt fișier obiect.

app: main.o lib.o print.o
	gcc $^ -o $@

%.o: %.c
	gcc -c $< -o $@
  • Din 11 linii au rămas 5. Un modul nou are nevoie doar ca fișierul lui obiect să fie adăugat în lista lui app.

make are și reguli predefinite: fără nicio regulă pentru main.o, tot compilează main.c, cu cc -c. Scrieți totuși propriile reguli, ca să alegeți voi comenzile.

Variabile​

O variabilă păstrează o valoare într-un singur loc: o definiți cu NAME = value și o folosiți cu $(NAME). Două nume sunt o convenție, pe care o așteaptă orice programator C:

CCcompilatorul de Cgcc
CFLAGSopțiunile compilatorului-Wall -g
CC = gcc
CFLAGS = -Wall -g

app: main.o lib.o print.o
	$(CC) $^ -o $@

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@
[student@fedora project]$ make -B

gcc -Wall -g -c lib.c -o lib.o
gcc -Wall -g -c print.c -o print.o
gcc main.o lib.o print.o -o app
[student@fedora project]$ make -n -B CFLAGS=-O2

...

Ținte false​

Unele ținte nu sunt fișiere: sunt nume pentru o acțiune pe care i-o cereți lui make. clean șterge ce a construit make:

clean:
	rm -f *.o app

make clean rulează rm de fiecare dată, pentru că nu există niciodată un fișier numit clean. Dacă însă apare unul, clean nu are dependențe și fișierul există, deci este la zi, iar rm nu mai rulează:

[student@fedora project]$ touch clean
[student@fedora project]$ make clean
make: 'clean' is up to date.

Ținta specială .PHONY listează țintele care nu sunt fișiere, numite ținte false (phony targets): make nu caută fișiere cu numele lor și le rulează întotdeauna rețetele. Țintele false obișnuite sunt:

installcopiază programul într-un director din PATH, ca să-l puteți rula după nume din orice director
uninstallșterge ce a copiat install

Dependențe de headere​

Și un header este o dependență: un fișier obiect trebuie compilat din nou când se modifică un header inclus de fișierul lui .c. Cu Makefile-ul de mai sus, make nu știe lucrul acesta:

[student@fedora project]$ sed -i 's/MAX 10/MAX 100/' lib.h
[student@fedora project]$ make
make: Nothing to be done for 'all'.
[student@fedora project]$ ./app
sum = 55
  • Suma numerelor de la 1 la 100 este 5050, dar main.o nu a fost compilat din nou: lib.h nu apare în nicio regulă.

Dependențele urmează liniile #include. Uitați-vă la liniile #include din fiecare fișier .c și adăugați fiecare header la regula fișierului lui obiect:

main.o: lib.h print.h
lib.o: lib.h
print.o: print.h
  • Aceste reguli nu au rețetă: doar adaugă dependențe, iar rețeta vine tot din %.o: %.c. Puneți-le la finalul Makefile-ului, ca all să rămână prima țintă.
[student@fedora project]$ make
gcc -Wall -g -c main.c -o main.o
gcc -Wall -g -c lib.c -o lib.o
gcc main.o lib.o print.o -o app
[student@fedora project]$ ./app
sum = 5050
  • main.c și lib.c includ lib.h, așa că fișierele lor obiect au fost compilate din nou; print.o a rămas neschimbat.
atenție

Un header se pune pe regula unui fișier obiect, niciodată pe regula executabilului: cu app: main.o lib.o print.o lib.h, make doar leagă din nou vechiul main.o, în care MAX este tot 10.

Ce trebuie să știe clangd​

clangd verifică fiecare fișier așa cum l-ar compila gcc, deci are nevoie de aceleași opțiuni, precum -I <DIR>. Fără ele, un header dintr-un alt director dă eroarea '<HEADER>' file not found în editor, chiar dacă make funcționează. Opțiunile i le dați într-un fișier din directorul proiectului:

FișierCe conțineCum îl creațiCând îl folosiți
compile_flags.txtopțiunile lui gcc, câte una pe linie, aceleași pentru toate fișierelede mână, în editor: de exemplu, linia -Iincludetoate fișierele folosesc aceleași opțiuni
compile_commands.jsoncomanda gcc exactă pentru fiecare fișier, așa cum a rulat-o makemake clean, apoi bear -- make; din nou după ce adăugați un fișierfișierele folosesc opțiuni diferite sau o redenumire trebuie să modifice toate fișierele

bear (Fedora: sudo dnf install bear; Ubuntu: sudo apt install bear) notează fiecare comandă pe care o rulează make, așa că porniți de la o compilare curată. Cu compile_commands.json, clangd cunoaște și fișierele pe care nu le-ați deschis: o redenumire le modifică pe toate. Ce află clangd, adică indexul proiectului, se păstrează în directorul .cache, care nu intră în repository (vedeți Salvarea versiunilor).

clangd --check=<FILE> verifică un fișier în terminal; ultima linie se termină cu All checks completed, 0 errors când fișierul nu are nicio eroare.

Depanarea: gdb​

Un debugger (depanator) rulează un alt program sub controlul lui: îl oprește la o anumită linie, îl rulează linie cu linie și îi afișează variabilele, în timp ce programul rulează. Este mai rapid decât să adăugați linii cu printf și să compilați din nou. gdb este debuggerul proiectului GNU. Are nevoie ca programul să fie compilat cu -g, care adaugă informațiile de depanare: ce cod mașină provine din ce linie și unde se află fiecare variabilă. Makefile-ul proiectului are deja -g în CFLAGS.

ComandăScurtCe face

break <PLACE> if <CONDITION>se oprește acolo doar când condiția C este adevărată: break sum if n > 5
watch <VARIABLE>se oprește de fiecare dată când variabila se schimbă și afișează valoarea veche și pe cea nouă
delete <N>dșterge breakpointul cu numărul <N>; fără <N>, le șterge pe toate

Salvarea versiunilor: git​

Git este un sistem de control al versiunilor (version control system): păstrează istoricul fișierelor unui proiect. Puteți reveni la orice versiune, puteți vedea ce s-a schimbat și de ce și puteți lucra la același cod împreună cu alți oameni. Directorul cu fișierele și istoricul lor (păstrat în directorul ascuns .git) se numește repository. Un commit este o fotografie a tuturor fișierelor, cu un autor, o dată și un mesaj; numele lui este un hash, de exemplu ed6ba3b.

Gândiți-vă la punctele de salvare dintr-un joc: salvați când lucrurile merg și vă puteți întoarce oricând la un punct de salvare.

O modificare trece prin trei locuri de pe calculatorul vostru: editați fișierele, git add le pune în zona de staging (staging area, ce va conține următorul commit), iar git commit salvează commitul în repository.

ComandăCe face

git inittransformă directorul curent într-un repository

git commit -m "<MESSAGE>"salvează zona de staging ca un commit

Lucrul cu GitHub​

Primii pași folosesc doar calculatorul vostru; exercițiile pentru acasă și provocările folosesc și GitHub.

Un commit rămâne doar pe calculatorul vostru. Un depozit la distanță (remote) este o copie a repository-ului pe un server, precum GitHub, GitLab sau Codeberg: în el vă trimiteți (push) commiturile și din el aduceți (pull) commiturile colegilor. Un coleg începe prin a clona repository-ul: obține o copie a fișierelor și a întregului istoric, legată de același remote, origin.

Gândiți-vă la un director partajat în cloud, care păstrează fiecare punct de salvare, împreună cu autorul lui.

ComandăCe face
git remote add origin <URL>leagă repository-ul de remote-ul <URL>, sub numele origin
git remote -vlistează remote-urile
git push -u origin maintrimite prima dată main către origin; -u ține minte alegerea, apoi ajunge git push
git push origin <BRANCH>trimite o altă ramură
git pulladuce commiturile noi din origin și le unește (merge) cu ramura curentă
git clone <URL> <DIR>copiază repository-ul în <DIR>, cu origin deja setat
git branch -d <BRANCH>șterge o ramură locală care a fost unită
git push origin --delete <BRANCH>șterge o ramură de pe remote
git config --global pull.rebase falsegit pull face merge când ambele părți au commituri noi; o singură dată pe fiecare calculator

GitHub nu acceptă parola în terminal. Folosiți o cheie SSH: o pereche de fișiere, o cheie privată, care nu părăsește niciodată calculatorul, și o cheie publică, pe care i-o dați lui GitHub. Cu o cheie, URL-ul unui repository are forma git@github.com:<USER>/<REPO>.git. Creați cheia o singură dată pe fiecare calculator:

ssh-keygen -t ed25519 -C "<EMAIL>"    # apăsați Enter la fiecare întrebare
cat ~/.ssh/id_ed25519.pub             # lipiți-o în GitHub: Settings, SSH and GPG keys, New SSH key
ssh -T git@github.com                 # răspundeți yes prima dată
  • Când GitHub vă cunoaște cheia, ssh -T git@github.com afișează Hi <USER>! You've successfully authenticated, but GitHub does not provide shell access.

Un pull request (PR) este o cerere, făcută pe GitHub, de a uni o ramură în main. Colegii citesc modificările în tab-ul Files changed, le comentează și apasă Merge pull request; apoi toată lumea rulează git pull. Regula majorității echipelor: nu faceți commituri direct pe main; creați o ramură, trimiteți-o și deschideți un pull request.

O bibliotecă este un fișier cu funcții compilate, gata de folosit de alte programe: printf se află în biblioteca C, sqrt în biblioteca matematică. Există două tipuri:

  • hello-static este totuși mai mic decât biblioteca C (stat -L -c '%s' /lib64/libc.so.6 afișează peste 1 MiB): linkerul a copiat doar părțile din bibliotecă pe care le folosește programul.

Vă puteți construi propriile biblioteci. -l<NAME> leagă lib<NAME>.so sau, dacă nu există, lib<NAME>.a; le caută în directoarele date cu -L <DIR>, apoi în directoarele sistemului (/usr/lib64 pe Fedora):

  3. Reparați compilarea: make eșuează în ~/exam/broken. Reparați-l fără să modificați fișierele .c și .h și faceți ca și editorul să găsească headerele. → Erori de compilare · Dependențe de headere · Ce trebuie să știe clangd

    • fișierele .c și .h nu s-au schimbat.

Întrebări de recapitulare​

Folosiți ultimele 5 minute ale laboratorului ca să răspundeți la aceste întrebări împreună cu colegii și cu asistentul. La ultimele două nu există răspunsuri greșite.

  1. Care este diferența dintre un program compilat și unul interpretat? Ce fel de program este hello și ce fel este hello.sh?
  2. Care sunt cele patru etape ale lui gcc și ce fișier rezultă din fiecare?
  3. De ce este printf un simbol U în hello.o? Cine îl găsește și unde?
  4. Ce se pune într-un fișier .h și ce într-un fișier .c? De ce compilați fiecare fișier .c în propriul fișier obiect?
  5. Cum vă dați seama, dintr-o eroare de compilare, ce etapă a raportat-o?
  6. Ce face un server de limbaj și cum comunică editorul cu el?
  7. Cum decide make dacă rulează o rețetă? De ce are nevoie clean de .PHONY și pe ce regulă se pune un header?
  8. Care este diferența dintre git add și git commit? De ce nu sunt fișierele obiect în repository?
  9. Ce eroare de compilare v-a surprins cel mai mult astăzi?
  10. Ce unealtă din acest laborator veți folosi la următoarea temă în C?

Extra​

  1. Un debugger în editor: așa cum LSP-ul aduce clangd în editor, DAP (Debug Adapter Protocol) aduce debuggerul: breakpointuri și variabile chiar lângă cod. Zed și VS Code îl au inclus; nvim folosește pluginul nvim-dap. Cu amândouă, orice editor devine un IDE (Integrated Development Environment). → 07. Dezvoltarea aplicațiilor
  2. clang: un alt compilator de C, din proiectul LLVM, cu propriile mesaje. Instalați-l cu sudo dnf install clang (Ubuntu: sudo apt install clang) și construiți proiectul cu make -B CC=clang. → man clang
  3. Compiler Explorer: godbolt.org afișează codul în limbaj de asamblare al unei funcții C în timp ce o scrieți, pentru multe compilatoare și procesoare, și dă fiecărei linii de C și instrucțiunilor ei aceeași culoare. Încercați -O2 pe sum. → Compilatorul
  4. CMake și Meson: proiectele mari nu își scriu Makefile-ul de mână; o unealtă îl generează dintr-o descriere mai scurtă a proiectului. → cmake.org, mesonbuild.com
