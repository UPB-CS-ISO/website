    What the CPU runs

    Machine code

    Why it matters

    The processor only runs machine code. When your source is translated (before it runs, or while it runs) decides how fast the program is, when you see its mistakes, and what you give to the people who use it.

    what you write: source code, text
    for (int i = 0; i < 3; i++) {
    printf("Hello, %d!\n", i);
}
    what the CPU runs: machine code, bytes (x86-64)
    c7 45 fc 00 00 00 00   # i = 0
eb 1d                  # jump to the test
...
e8 00 00 00 00         # call printf
83 45 fc 01            # i++
83 7d fc 02            # i <= 2 ?
7e dd                  # if yes, jump back
    • every processor family has its own instruction set: these bytes mean nothing to an ARM64 or a RISC-V CPU
    • so the source must be translated to the machine code of this CPU: who does it, and when?

    Three answers

    $ gcc hello.c -o hello  # once
$ ./hello  # as many times as you want
Hello, 0!
$ file hello
hello: ELF 64-bit LSB pie executable, x86-64

    The executable is machine code: it runs without gcc, but only on x86-64 Linux.

    $ bash hello.sh  # read again, every time
Hello, 0!
$ file hello.sh /bin/bash
hello.sh:  Bourne-Again shell script, ASCII text
/bin/bash: ELF 64-bit LSB pie executable, x86-64

    The script is only text: the CPU runs bash, and bash does what the script says.

    Try it

    When is the mistake found?

    The clearest difference shows up when the code has a mistake. A compiler reads all of the file before anything runs; an interpreter finds a mistake only when it reaches that line.

    Line 3 hasC (gcc)Python (python3)bash
    a typo ())error, nothing runsSyntaxError, nothing runslines 1, 2 run, then the error
    a misspelled nameerror, nothing runslines 1, 2 run, then NameErrorlines 1, 2 run, an error, then line 4
    a change, not rebuiltruns the old coderuns the new coderuns the new code

    Why it matters

    A compiled program cannot crash on a typo: it would not have been built. A script can stop halfway, after it has already done part of its work (deleted some files, written half a report). Test every branch of a script, not only the first lines.

    The middle way

    Bytecode and virtual machines

    • javac compiles once, to bytecode: machine code for an imaginary CPU
    • the virtual machine (java) runs the bytecode on any OS and CPU it is installed on: write once, run anywhere
    • JIT (just in time): the VM watches which code runs often and compiles it to real machine code, while the program runs
    $ javac Hello.java
$ file Hello.class
Hello.class: compiled Java class data
$ java Hello
Hello, 0!

    Python and JavaScript are compiled too

    • you run the source, python3 total.py, but python3 first compiles all of the file to bytecode, then its VM runs it
    • that is why a SyntaxError anywhere stops the script before its first line runs
    • the bytecode of imported modules is kept in __pycache__/, so the next run starts faster
    • node, deno and Chrome share the V8 engine, which JIT-compiles the code that runs often
    $ cat total.py
total = total + i
$ python3 -m dis total.py  # the bytecode
  LOAD_NAME     0 (total)
  LOAD_NAME     1 (i)
  BINARY_OP     0 (+)
  STORE_NAME    0 (total)

    Only shells really read and run one command at a time.

    Compiled vs. interpreted

    A language is not compiled or interpreted

    The program that runs it is: C can be compiled by gcc or interpreted by picoc; Python can be run by python3 (bytecode) or compiled to an executable by nuitka.

    LSP

    The Language Server Protocol

    The problem

    • to understand C, an editor must parse it, follow the #includes and know the types: the work of a compiler
    • 5 editors × 5 languages = 25 plugins, each with its own C parser
    • with one protocol, 5 + 5 = 10 programs: every editor talks to every server

    LSP (Microsoft, 2016)

    The editor asks, the language server answers: clangd for C/C++, rust-analyzer, pyright, gopls ...

    How it starts

    1. you run hx main.c
    2. the editor sees a C file and starts clangd: fork + exec, a child process
    3. two pipes connect them: the code and questions to its stdin, answers and errors from its stdout
    4. you type, the editor sends the changes and shows the answers
    5. clangd crashes? the editor keeps working

    A conversation

    Three kinds of messages, all JSON: a notification (no answer: I opened main.c), a request with an id (what is under the cursor?) and the response with the same id.

    Also from the server: the errors while you type (diagnostics), go to definition, rename in every file.

    Instead of printf

    What is a debugger?

    Why it matters

    printf shows what you guessed to print. A debugger stops the program where you want and shows everything: variables, the call stack, memory. Most bugs are found faster this way.

    • breakpoints: stop at a line or a function
    • step: run one line at a time
    • inspect: variables, memory, the call stack
    • watchpoints: stop when a variable changes
    • change a variable and continue

    Debuggers: gdb (GNU), lldb (LLVM), the Visual Studio debugger.

    How it works

    1. gdb starts the program itself: fork + exec, app is its child, stopped before its first instruction
    2. the ptrace system call: gdb asks the kernel to read and write the memory and registers of app, to stop and continue it
    3. app reaches the breakpoint: the kernel stops it and tells gdb
    $ gdb -q ./app
Reading symbols from ./app...
(gdb) break sum
Breakpoint 1 at 0x1188: file lib.c, line 3.
(gdb) run
Breakpoint 1, sum (n=10) at lib.c:3
3           int s = 0;
(gdb) print n
$1 = 10
(gdb) next
4           for (int i = 1; i <= n; i++) {

    gdb -tui (or Ctrl+X A) shows the source above the commands: B+ a breakpoint, > the next line to run.

    Common mistake

    Debugging a program built without -g

    Without debug information the executable is only machine code: gdb cannot show lines or variable names.

    Instead: compile with gcc -g (a debug build); a release build usually leaves it out. Rust (cargo build), Go and javac -g add it too.

    DAP

    The Debug Adapter Protocol

    • the same problem as LSP: every debugger has its own commands (break in gdb, breakpoint set in lldb)
    • DAP (Microsoft, 2016): the editor asks, the debug adapter answers
    • the editor starts the adapter (e.g. lldb-dap), two pipes connect them, as for LSP
    • the adapter starts app and controls it with ptrace, like gdb
    LanguageDebug adapter
    C, C++, Rustlldb-dap, CodeLLDB, gdb -i=dap (gdb 14+)
    Pythondebugpy
    Godlv dap (Delve)
    JavaScript, TypeScriptjs-debug
    Four steps

    From hello.c to an executable

    Why it matters

    Every build error comes from one of the four steps: a missing header from the preprocessor, a type error from the compiler, an undefined reference from the linker. Know the step, and the message makes sense.

    Stop after any step

    Stop afterCommandYou getLook at it with
    1. preprocessorgcc -E hello.c -o hello.ihello.i, C textwc -l, tail
    2. compilergcc -S hello.chello.s, assemblycat
    3. assemblergcc -c hello.chello.o, an object filenm, objdump -d, file
    4. linkergcc hello.o -o hellohello, the executablefile, ldd, ./hello

    gcc -save-temps hello.c -o hello keeps all of them: hello.i, hello.s, hello.o.

    To read hello.s: -fverbose-asm writes each line of C as a comment above its instructions; -masm=intel writes the Intel syntax of the processor manuals instead of AT&T. For an object built with gcc -g, objdump -d -S -M intel shows each line of C above its machine code.

    Static and shared

    Libraries

    A library is a file of compiled functions, ready for other programs: printf is in the C library, sqrt in the math library. The two kinds differ in when the code of the library joins the program: when it is linked (static) or every time it starts (shared).

    Static (libNAME.a)Shared (libNAME.so, the default)
    the linkercopies the functions into the executableonly writes down that the executable needs the library
    when the program startsnothing to loadthe loader (ld-linux-x86-64.so.2) finds and loads the .so
    a new version of the librarylink every program againevery program uses it at its next start
    the library is not installedthe program still runserror while loading shared libraries
    sizeevery program has its own copy (hello-static: 636K)one copy for all (hello: 12K)

    The commands

    CommandWhat it does

    gcc -fPIC -c lib.c, then gcc -shared lib.o -o libsum.soa shared library (-fPIC: code that works at any address)
    gcc main.o print.o -L. -lsum -o applink with libsum: -L. looks in this folder; .so is preferred to .a

    LD_LIBRARY_PATH=. ./apprun app, and let the loader also look in .
    Compile once, link often

    Several files and build errors

    $ gcc -c main.c
$ gcc -c lib.c
$ gcc -c print.c
$ gcc main.o lib.o print.o -o app
$ vim print.c  # edit
$ gcc -c print.c  # only this one
$ gcc main.o lib.o print.o -o app
    • compile each .c to its own .o, then link them into app
    • after a change, compile again only the file that changed, then link again
    • in a big project this saves minutes on every build; remembering what changed is the job of make

    Which step complains?

    The first words of the message tell the step: file.c:line:column: comes from the preprocessor or the compiler, /usr/bin/ld: from the linker.

    1 · preprocessor
    main.c:1:10: fatal error: lib.h: No such file or directory

    The #included file is not found: a wrong name, or a folder missing (-I dir).

    2 · compiler
    main.c:6:17: error: implicit declaration of function 'sum' [-Wimplicit-function-declaration]

    sum is used, but nothing declared it: the #include "lib.h" is missing. (An error since GCC 14.)

    4 · linker
    /usr/bin/ld: main.o: in function `main':
main.c:(.text+0x13): undefined reference to `sum'

    Every file compiled, but no object file defines sum: lib.o is missing from the command.

    4 · linker
    /usr/bin/ld: calc.o: in function `main':
calc.c:(.text+0x2a): undefined reference to `sqrt'

    The function is in a library that is not linked: add -lm (the math library).

    Check yourself

    gcc main.o print.o -o app fails with undefined reference to 'sum'. Which step complains?

    Rules: target, prerequisites, recipe

    A Makefile

    Why it matters

    make runs only the commands that are needed, in the right order. Almost every C project (and these slides) is built with a Makefile; its mistakes, like a forgotten header, give programs that run with old code.

    ~/hello/Makefile
    hello: hello.o
	gcc hello.o -o hello

hello.o: hello.c
	gcc -c hello.c
    • a Makefile is a list of rules, one for every file that is built
    • target: the file to build, before the :
    • prerequisites: the files it is built from, after the :
    • recipe: the commands that build it, on the next lines, each starting with a TAB
    • hello: hello.o: hello is built from hello.o, by linking it
    • make reads the Makefile of the current directory and builds the first target, here hello; make hello.o builds only that one
    • it compares the modification times of the files (ls -l) and runs a recipe only when the target is older than what it is built from
    Common mistake

    Spaces instead of a TAB

    Makefile:2: *** missing separator. Stop.: the recipe line starts with spaces.

    Instead: set the editor to keep TABs in a Makefile.

    Step by step

    How make runs the targets

    The project: main.c calls sum from lib.c and print_result from print.c. Each .c is compiled to its own .o, and the three .o files are linked into app.

    1. start from the goal: the first target (app), or the one you name (make lib.o)
    2. make every prerequisite first, the same way: the stack of targets grows
    3. a prerequisite with no rule must exist as a file, else No rule to make target
    4. run the recipe only if the target is missing or older than a prerequisite
    5. a command fails? make stops: Error 1
    ~/project/Makefile
    app: main.o lib.o print.o
	gcc main.o lib.o print.o -o app

main.o: main.c
	gcc -c main.c

lib.o: lib.c
	gcc -c lib.c

print.o: print.c
	gcc -c print.c

    make reads only the times

    It never looks inside the files: touch (a new modification time) is enough to rebuild. make --debug=v prints every decision: Considering target file ..., Prerequisite 'print.c' is newer than target 'print.o', Must remake target ....

    From four rules to %.o: %.c

    A shorter Makefile

    The three .o rules are the same, only the names change. Three steps make the Makefile shorter; make runs exactly the same commands.

    1. Automatic variables: $@, $<, $^

    Makefile
    app: main.o lib.o print.o
	gcc $^ -o $@

main.o: main.c
	gcc -c $< -o $@

lib.o: lib.c
	gcc -c $< -o $@

print.o: print.c
	gcc -c $< -o $@
    • in a recipe, $@ is the target, $< the first prerequisite, $^ all the prerequisites
    • make fills them in for each rule, before it runs the command: gcc -c $< -o $@ becomes gcc -c main.c -o main.o
    • now the three .o rules have the same recipe
    MeansIn main.o: main.cIn app: main.o lib.o print.o
    $@the targetmain.oapp
    $<the first prerequisitemain.cmain.o
    $^all the prerequisitesmain.cmain.o lib.o print.o

    2. A pattern rule: %.o: %.c

    Makefile
    app: main.o lib.o print.o
	gcc $^ -o $@

%.o: %.c
	gcc -c $< -o $@
    • % matches any name: %.o: %.c says *any .o is built from the .c with the same name*
    • to make lib.o, make finds no rule named lib.o, tries the pattern with % = lib, and checks that lib.c exists
    • the recipe is the same for all of them, thanks to $< and $@
    • a new util.c? add util.o to app, nothing else

    3. Variables: CC and CFLAGS

    ~/project/Makefile
    CC = gcc
CFLAGS = -Wall -g

app: main.o lib.o print.o
	$(CC) $^ -o $@

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@
    • NAME = value defines a variable, $(NAME) uses it
    • CC: the compiler, CFLAGS: its options (-Wall all warnings, -g debug information)
    • change the compiler or the options in one place
    • make prints the commands after filling in the variables: gcc -Wall -g -c main.c -o main.o

    The Makefile is not a prerequisite

    Change CFLAGS and make says up to date: the .o files are newer than the .c files. make -B (or make clean, then make) rebuilds everything with the new options.

    clean, all, run, .PHONY

    Special targets

    ~/project/Makefile
    CC = gcc
CFLAGS = -Wall -g

.PHONY: all build run clean

all: build

build: app

run: build
	./app

app: main.o lib.o print.o
	$(CC) $^ -o $@

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

clean:
	rm -f *.o app
    • clean, all, build, run are targets that are not files
    • all: build and build: app have no recipe: they only name what to build
    • run: build first builds, then runs ./app
    • if a file named clean existed, make clean would say up to date and delete nothing
    • .PHONY tells make they are not files: their recipe always runs
    • all, clean, install, check are GNU conventions

    make clean && make builds everything from scratch, like make -B.

    Where do the .h files go?

    Header dependencies

    • main.o is built from main.c and from the two headers it #includes
    • lib.h is needed by two object files: main.o and lib.o
    • the short Makefile lists only the .c files: change MAX in lib.h, and make says up to date: app still prints 55, not 5050
    main.c
    #include "lib.h"
#include "print.h"

int main(void)
{
    int total = sum(MAX);
    print_result("sum", total);
    return 0;
}
    Common mistake

    lib.h on app

    app: main.o lib.o print.o lib.h only links again: main.o keeps the old MAX, still 55 (and gcc gets lib.h in $^).

    Instead: a header goes on the rule of every .o whose .c includes it, never on the executable.

    the fix: add these lines to the Makefile
    main.o: lib.h print.h
lib.o: lib.h
print.o: print.h

    Bonus: automatic dependencies

    Makefile
    CC = gcc
CFLAGS = -Wall -g -MMD
OBJS = main.o lib.o print.o

app: $(OBJS)
	$(CC) $^ -o $@

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

-include $(OBJS:.o=.d)
    $ cat main.d lib.d print.d
main.o: main.c lib.h print.h
lib.o: lib.c lib.h
print.o: print.c print.h

    -MMD: gcc writes the headers each file includes into a .d file, and the Makefile includes them. (Not in the demo terminal.)

    Save points for your code

    What is Git?

    Why it matters

    Every lab and homework is handed in through a Git repository, and every software team works with one. Git keeps every version, shows who changed what, and lets several people change the same code.

    • a version control system: keeps the history of the files
    • go back to any version, see who changed what and why
    • distributed: every copy has the whole history
    • written in 2005 by Linus Torvalds, for Linux
    • the folder with the files and their history is a repository (repo)
    • a commit is a snapshot of the files, with a message and an author: a save point, like in a game
    • every commit points to its parent: the chain is the history (git log --oneline)
    • a branch is a name for a commit that moves forward with every new commit; HEAD is the branch you are on

    Four places

    PlaceWhat is thereCommand that moves a change to the next place
    working directorythe files you editgit add picks what goes in the commit
    staging areathe next commitgit commit saves it in the local repository
    local repositorythe history, on your computergit push sends it to the remote
    remote repositoryGitHub, GitLab ..., sharedgit pull brings the others' commits

    Commit is not push

    git commit saves only on your computer: your colleagues (and your teacher) do not see it. git status says Your branch is ahead of 'origin/main' by 1 commit until you git push.

    Common mistake

    Trusting every folder

    Opening a project can run code: the language server and tasks the folder's settings name, and for Rust, rust-analyzer builds the project and runs its build.rs as soon as the folder opens.

    Instead: open unknown code in restricted mode (do not trust the folder): you can read and edit it, nothing from it runs.
