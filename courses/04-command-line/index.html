    Many users, one computer

    The classic terminal: a keyboard and a screen

    Why it matters

    Every command you type goes through a terminal to a shell. They are two different programs, and knowing which one does what explains Ctrl+C, /dev/pts/0 and why closing a window can stop your programs.

    • the old terminals were TeleTypes, TTY: a keyboard and a printer, later a screen, but no processor
    • everything ran on the mainframe, the terminals only moved text in and out
    • Linux still calls terminals tty: /dev/tty1, /dev/tty2, ... are files in /dev
    Text mode

    Virtual terminals: /dev/tty1 ... /dev/tty6

    Your computer has one screen and one keyboard, but the kernel offers several virtual terminals on them. At start-up, a program waits for a login on each one; after the login, it becomes your shell.

    The graphical interface uses a terminal too

    The display server (Xorg or Wayland) takes over tty1 or tty2 and draws through the framebuffer, /dev/fb0. Ctrl+Alt+F3 ... F6 switch to a text terminal, Ctrl+Alt+F1 or F2 back.

    The terminal emulator and the shell

    Terminal and shell: two programs

    A shell is a process whose main job is to let you talk to the operating system. In a graphical session, its text is shown by a terminal emulator, another program.

    $ tty  # the terminal of the shell
/dev/pts/0
$ ps  # the processes of this terminal
    PID TTY          TIME CMD
   4100 pts/0    00:00:00 bash
   4300 pts/0    00:00:00 ps
    Kind of shellExamples
    command linebash, sh, zsh, fish, cmd, powershell
    text user interfacemc, nnn, yazi
    graphicalExplorer, Finder, nautilus, the Settings
    Check yourself

    You close the window of foot. Which program ended first?

    ✉️ A number from the kernel

    Signals: a message for a process

    A signal is a short message the operating system sends to a process: just a number (sometimes with one more number as payload). Ctrl+C, closing a window and kill all send one; kill -l lists them. When it arrives, the process runs the default action of the signal, or its own handler (next page).

    Exit code 128 + the signal number

    A process ended by a signal has the exit code 128 + N: 130 after Ctrl+C (2), 137 after kill -9, 143 after kill (15).

    Handling signals

    trap: your own handler

    When a signal arrives, the process stops what it does and runs the default action, or, if it registered one, its own signal handler; after a handler it goes on with its work. In bash: trap FUNCTION SIGNAL.

    The same in C

    #include <signal.h>

void handler(int signum) { /* ... */ }

signal(SIGINT, handler);
    • SIGKILL and SIGSTOP can never be caught, blocked or ignored: the last resort when a program does not listen
    • trap '' SIGINT (an empty handler) ignores the signal
    • programs use handlers to clean up: delete temporary files, save the work, then exit
    Check yourself

    A script has trap cleanup SIGTERM. Which command still ends it, with no cleanup?

    One in front, any number behind

    Foreground and background

    Why it matters

    A command that takes minutes (a download, a build, a server) does not have to block your terminal: put it in the background and keep working. The same keys and commands bring it back.

    Foreground

    • only one process (or pipeline)
    • it reads the keyboard (stdin)
    • the shell waits for it

    Background

    • any number of processes, called jobs
    • running or stopped
    • the shell does not wait: it shows the prompt
    Run in the background

    &: start a job

    Add & at the end: the shell starts the command and shows the prompt right away. It prints the job ID and the PID.

    Common mistake

    A job still writes to your terminal

    ls -R / & fills the screen while you type: the background only frees the keyboard, not the display.

    Instead: redirect the output of a job: find / -name '*.log' > logs.txt 2> /dev/null &.

    From the foreground to the background and back

    Ctrl+Z, bg, fg: move a job

    Forgot the &? Stop the foreground process with Ctrl+Z, then let it continue in the background with bg. fg brings a job back to the foreground.

    How the kernel groups the processes of a terminal

    Sessions, groups and the controlling terminal

    The kernel groups the processes of a terminal in two levels: a process group is one job, a session is all the groups of one terminal. One group is in the foreground: only it gets the keys.

    SIGKILL cannot be caught

    When bash is killed

    Normally bash forwards SIGHUP to its jobs when the terminal closes. If bash is killed with SIGKILL, it cannot forward anything.

    Check yourself

    You start nohup ./backup.sh > backup.log & and close the terminal. What happens to the script?

    Keys and signals

    Ctrl+C, Ctrl+\ and Ctrl+Z

    The terminal driver in the kernel turns some keys into signals for the whole foreground group.

    KeysSendsDefault action
    Ctrl+CSIGINTterminate (interrupt) the process
    Ctrl+ZSIGTSTPstop the process, it becomes a stopped job
    Ctrl+\SIGQUITterminate it and write a core dump
    Ctrl+Dno signalend of file: stdin has nothing more to read

    Only the foreground reads the keyboard

    A job that tries to read the keyboard gets SIGTTIN and is stopped. bg and fg send SIGCONT to continue a stopped job.

    Every process has one

    The environment: NAME=value texts

    • every process has a list of NAME=value texts: its environment
    • a process receives it from its parent: fork copies it, exec keeps it
    • programs read it to configure themselves: getenv("HOME") in C, $HOME in bash
    • the names are in UPPER CASE, by convention
    $ printenv HOME  # one variable
/home/student
$ echo "I am $USER"  # the shell replaces $USER
I am student
$ env  # all of them
    bash · PID 4100 · environment

    USERstudent
    SHELL/bin/bash
    PATH/home/student/.local/bin:/usr/local/bin:/usr/bin:/bin
    LANGen_US.UTF-8
    PWD/home/student
    A copy, never a link

    Inherited by the children

    Every process starts with a copy of the environment of its parent. A process passes variables down to its children, never up.

    Only the exported ones are passed on

    export: shell variables and environment variables

    NAME=value creates a shell variable: only this shell has it. export NAME makes it an environment variable: the children get a copy.

    Common mistake

    Spaces around =

    GREETING = hello runs a command named GREETING with two parameters: bash: GREETING: command not found.

    Instead: no spaces: GREETING=hello; quotes for a value with spaces: GREETING="hello world".

    Already there when the prompt shows up

    Defined by the shell

    VariableValueDefined in (Fedora)
    HOME, USER, SHELLthe home directory, the user, the shell/etc/passwd, read by login
    PWD, OLDPWDthe current and the previous directorythe shell, at every cd (cd - uses OLDPWD)

    The startup files are shell scripts: they run export NAME=value (or NAME=value for PS1).

    Special parameters

    • $?: the exit code of the last command (0 means success)
    • $$: the PID of the shell
    • $!: the PID of the last job started with &
    • they are set by the shell; you can only read them
    $ ls /nope
ls: cannot access '/nope': No such file or directory
$ echo $?  # ls failed: not 0
2
$ echo $?  # the exit code of echo
0
$ echo $$
4100

    export NAME=valuean environment variable, for this shell and every command started after it
    NAME=value commandan environment variable only for command, the shell does not keep it

    Cheat sheet and practice

    The parts of a line

    A command line: assignments, command, parameters, redirects

    Before the command starts, the shell cuts the line into parts. Only the assignments must be at the start; the redirects can be anywhere.

    $ LANG=C sort -r "$HOME/my notes.txt" my\ list.txt *.csv > sorted.txt 2> errors.txt
    LANG=Cassignments (optional)sortthe command-r"$HOME/my notes.txt"my\ list.txt*.csvits parameters>sorted.txt2>errors.txtredirects (anywhere)
    • NAME=value words at the start: variables only for this command
    • the first word that is not an assignment or a redirect is the command
    • everything else is a parameter: options, file names, texts
    • a redirect (>, 2>, <) and its file name are for the shell, not for sort

    Mixed order

    $ IN="my notes.txt" OUT=sorted.txt OPTS="-u -f"
$ LANG=C 2> errors.txt sort "$IN" '$IN' > "$OUT" -r $OPTS -t ',' *.csv
    LANG=Cassignment2>errors.txtredirectsortcommand"$IN"'$IN'parameters>"$OUT"redirect-r$OPTS-t','*.csvparameters
    What the shell does before the command starts

    Splitting a line, step by step

    The shell works on the line in a fixed order: it splits it into words, sets the assignments and redirects apart, replaces the variables, splits the results, expands the globs, removes the quotes, and only then starts the command.

    From left to right

    The order of redirects

    The shell applies the redirects from left to right. 2>&1 means: 2 goes where 1 goes now. It is a copy, not a link: changing 1 later does not change 2.

    $ ls /etc /nope > all.txt 2>&1  # nothing on the display
$ ls /etc /nope 2>&1 > all.txt  # the error is on the display
ls: cannot access '/nope': No such file or directory
    Quoting and escaping

    Quotes and \: what the command receives

    Spaces, $, * and the quotes are special for the shell. The quotes and the \ tell it to treat them as plain characters; then the shell removes them: the command only gets the words.

    • '...' single quotes: nothing inside is special
    • "..." double quotes: $NAME is replaced, the result stays one word, the spaces are kept
    • \ before a character: that one character is plain
    Globbing

    Globs: patterns for file names

    An unquoted *, ? or [...] is a pattern: the shell replaces it with the names of the matching files, sorted, before the command starts. The command never sees the pattern.

    Common mistake

    Quote a pattern that is for the command

    find . -name *.txt is expanded by the shell first: find gets -name fruits.txt my list.txt ... and fails.

    Instead: find . -name '*.txt': the quotes keep the * for find.

    Not every command is a program

    Built-in and external commands

    Built-in commands

    • run inside the shell, no new process
    • cd, export, unset, jobs, fg, bg, type, exit, echo

    External commands

    • executable files, somewhere on the disk
    • the shell needs their path
    • ls, sort, grep, bash
    $ type cd
cd is a shell builtin
$ type sort
sort is /usr/bin/sort
    Check yourself

    Why must cd, unset and exit be built into the shell?

    How the shell finds the program

    Which file? A path, a builtin or a PATH search

    For an external command the shell needs a path. A first word with a / is a path already; a plain name is looked up in the directories of the PATH variable, from left to right.

    🐧 exec only starts a path: turning a name into a path is the job of the shell (of the C library, in fact: the shell calls execvp).
    The PATH in the demo terminal

    which, type and practice

    $ which sort  # the PATH search, without running sort
/usr/bin/sort
$ which -a sort  # every match, in the order of PATH
/usr/bin/sort
/bin/sort
$ which cd  # nothing found: no output
$ echo $?
1
    • which prints the file the shell would run
    • -a prints every match
    • which is an external command: it only searches PATH, it does not know the builtins; type cd asks the shell itself
    • the current directory is not in PATH: that is why you run ./hello
