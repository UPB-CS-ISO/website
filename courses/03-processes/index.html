    The Linux app store, long before the app stores

    App repositories

    Why it matters

    Every program you use in the labs is installed from the repository of your distribution. Knowing what a package and a dependency are explains why apt asks for sudo, why it installs ten packages for one, and why removing a program leaves others behind.

    • applications come as packages: the program, its files and the list of packages it needs (dependencies)
    • the distribution keeps them in a repository: a server with thousands of checked and signed packages
    • the package manager searches, downloads, installs, updates and removes them, dependencies included

    🌐 Repository

    cowsay, git, firefox ... and what each one needs: cowsay → perl, firefox → gtk3. Checked and signed by the distribution.

    ⚙️ Package manager

    Fedora: dnf, packages .rpm. Ubuntu: apt, packages .deb. Search, download, check, install, update, remove.

    Files to actions

    Executable vs. process

    Why it matters

    The operating system offers two abstractions: files for data and processes for actions. Every command you type becomes a process; most of the tools in this lecture (ps, redirects, /proc) look at or change one.

    • an executable is a file on the disk: /bin/ls
    • a process is a running instance of it, with its own memory, open files and PID
    • one executable can run as many processes at the same time: three terminals running bash are three processes of /usr/bin/bash
    • peripherals are files too (POSIX): /dev/sda the first disk, /dev/input/... the keyboard, /dev/fb0 the screen
    The loader

    Loading an executable

    1. program loading: the loader reads the executable and copies its code and data into memory
    2. library loading: it finds the libraries the program needs (libc.so.6, ...) and loads them too
    3. runtime dynamic linking: it connects the calls of the program to the functions inside the libraries
    4. execution: the processor jumps to the start of the program; the code of the program and of the libraries runs

    An executable file holds three things: how to load it, the actual code, and the links to the libraries it needs.

    From Ready to Done

    Process states

    Why it matters

    Most processes spend their life waiting: for you to type, for the disk, for the network. The state explains why a computer with 300 processes is not slow, and what the R, S and Z in ps mean.

    StateMeaningps
    Readyhas everything it needs, waits for a free processorR
    Runningits code runs; when its time slice ends it goes back to ReadyR
    Waitingwaits for an event: disk data, a key, a network packet; it does not use the processorS
    Donehas finished (exit), waits for the parent to read its exit codeZ
    $ ps -e -o pid,stat,comm
    PID STAT COMMAND
      1 Ss   systemd
   4100 Ss   bash
   4210 S    sleep
   4211 R    yes
   4213 Sl   myapp
   4214 Z    myapp-worker <defunct>
   4220 R+   ps

    bash waits for you to type, sleep for its timer; yes computes all the time. The other letters: s session leader, l several threads, + in the foreground.

    Check yourself

    ps shows S for a text editor you are not typing in. Is something wrong?

    fork, exec, exit, wait

    Creating a process

    Why it matters

    Every process except the first one is created by another process. The shell runs each command with the same four calls, so redirects, the PPID and zombies all come from this mechanism.

    1. the parent calls fork: it makes a clone of itself, from now on there are two identical processes
    2. the child calls exec: it replaces its executable with another one (same PID)
    3. the child eventually calls exit (or returns from main) with an exit code
    4. the parent does other work or waits; it calls wait to read the exit code of the child
    Check yourself

    After fork, which of these is different in the child?

    The first process

    How Linux starts

    • the kernel starts one user-space process, init, with PID 1; on most distributions it is systemd
    • init starts the services: devices, network, the login screen, then your session
    • every other process descends from it: pstree shows the whole family
    • the kernel also runs its own threads (kthreadd, kworker), shown in brackets in ps

    init cannot stop

    If PID 1 ends, the kernel panics: the whole system stops. The next chapter shows why.

    $ pstree -p
systemd(1)
├─systemd-udevd(512)
├─NetworkManager(640)
└─systemd(1000)
  └─gnome-terminal-(4090)
    └─bash(4100)
      └─pstree(4301)
    The parent ends first

    Orphan processes

    • when a parent ends, its children keep running without a parent: they are orphans
    • the kernel reparents them to init (PID 1): their PPID becomes 1
    • init calls wait for them when they end
    The parent never calls wait

    Zombie processes

    • a process that has finished stays Done until its parent reads its exit code with wait
    • meanwhile the system keeps its PID and its entry in the process table: allocated, but not used, a 🧟 zombie (Z, <defunct> in ps)
    • a zombie cannot be killed: it is already dead; only its parent calling wait, or the parent ending, removes it

    🐧 + 🧟 = 🛑

    Without init there is nobody to adopt orphans and nobody to wait for them: the system would fill with zombies. Linux does not allow it: it panics when init stops.

    Check yourself

    ps shows hundreds of <defunct> processes with the same PPID. Whom do you fix?

    How processes access data

    The File Descriptor Table

    Why it matters

    A process never writes to the display or reads from the keyboard by name: it writes to 1 and reads from 0. The shell decides what those numbers point to, and that is the whole trick behind redirects and pipes.

    • each process has a File Descriptor Table
    • every open file has an entry; the index in the table is the file descriptor
    • a new file goes at the first free index
    fdnamepoints to, by default
    0stdinthe keyboard
    1stdoutthe display
    2stderrthe display, for errors
    The process opens the file by itself

    sort opens a file

    $ cat fruits.txt
cherry
apple
banana
$ sort fruits.txt  # the file name is an argument
apple
banana
cherry
    1. the shell starts sort with 0, 1 and 2, and gives it fruits.txt as an argument
    2. sort calls open("fruits.txt"); the kernel places it at the first free index: 3
    3. sort reads the lines from 3, sorts them and writes them to 1; the keyboard (0) is not used
    sort fruits.txt · File Descriptor Table
    0stdin→ keyboard
    1stdout→ display
    2stderr→ display
    3opened→ fruits.txt
    A file replaces the keyboard

    <: redirect stdin

    $ sort  # reads the keyboard, until Ctrl+D
$ sort < fruits.txt  # reads fruits.txt
apple
banana
cherry
    • without a file name sort reads 0, the keyboard
    • with < fruits.txt the shell opens the file and puts it at 0 before it starts sort
    • sort does not know: it reads 0, as always
    sort < fruits.txt · File Descriptor Table
    0stdin→ fruits.txt
    1stdout→ display
    2stderr→ display
    Common mistake

    sort fruits.txt and sort < fruits.txt are the same

    The output is, the mechanism is not. With an argument, sort opens the file itself (at 3) and knows its name; with < the shell opens it at 0 and sort only sees a stream. That is why wc -l fruits.txt prints the name and wc -l < fruits.txt does not.

    Instead: use < for commands that only read stdin, or when the name must not appear.

    The display is replaced by a file

    > and >>: redirect stdout

    $ ls > files.txt  # nothing on the display
$ cat files.txt
Movies
notes.txt
todo.txt
$ echo one > log.txt  # empty the file, then write
$ echo two >> log.txt  # write at the end
$ cat log.txt
one
two
    ls > files.txt · File Descriptor Table
    0stdin→ keyboard
    1stdout→ files.txt
    2stderr→ display
    the shell opens the file withwrites go
    >O_WRONLY | O_CREAT | O_TRUNCafter the file is emptied
    >>O_WRONLY | O_CREAT | O_APPENDat the end, always

    > empties the file first

    Even before the command runs: sort fruits.txt > fruits.txt leaves an empty file, because the shell truncates fruits.txt before sort reads it. Use >> for logs, so every command adds its lines.

    Errors into a file

    2>: redirect stderr

    $ ls /nope  # the error is on the display
ls: cannot access '/nope': No such file or directory
$ ls /nope 2> errors.txt  # nothing shows up
$ ls /nada 2>> errors.txt  # append the error
$ ls /etc /nope > all.txt 2>&1  # both, into one file
$ ls /etc /nope &> all.txt  # the same, shorter
    ls /nope 2> errors.txt · File Descriptor Table
    0stdin→ keyboard
    1stdout→ display
    2stderr→ errors.txt
    • only 1 (stdout) changes with >; errors still reach the display through 2
    • > out.txt 2> errors.txt separates them
    • 2>&1 makes 2 point where 1 points now: write it after > all.txt

    Heredoc

    $ cat <<EOF

    The lines up to EOF are sent as they are to stdin; a # there is not a comment. (The demo terminal does not do heredocs.)

    The stdout of one process is the stdin of the next

    |: pipe

    1. the shell creates a pipe: a buffer in the kernel with a write end and a read end
    2. it starts ls with the write end at index 1
    3. it starts wc with the read end at index 0
    4. both run at the same time: wc reads what ls writes, until ls ends (end of file)
    $ ls
Movies  notes.txt  todo.txt
$ ls | wc -l
3

    No temporary file is used. ls prints one name per line when its 1 is not a terminal.

    ls · File Descriptor Table
    0stdin→ keyboard
    1stdout→ pipe (write end)
    2stderr→ display
    │ pipe ▼
    wc -l · File Descriptor Table
    0stdin→ pipe (read end)
    1stdout→ display
    2stderr→ display
    Devices made by the kernel

    Special files

    🕳️ /dev/null

    everything written is discarded; reading gives end of file right away. ls /nope 2> /dev/null hides the error.

    0️⃣ /dev/zero

    reading gives as many 0 bytes as asked; writes are discarded.

    🎲 /dev/urandom

    reading gives as many random bytes as asked: keys, passwords, random names.

    $ xxd -l 8 < /dev/zero  # the first 8 bytes
00000000: 0000 0000 0000 0000                      ........
$ xxd -l 8 < /dev/urandom  # different every time
00000000: 9f3a 51c2 07e8 b4d1                      .:Q.....
$ ls -l /dev/null /dev/zero /dev/urandom
crw-rw-rw- 1 root root 1, 3 Oct 12 09:12 /dev/null
crw-rw-rw- 1 root root 1, 5 Oct 12 09:12 /dev/zero
crw-rw-rw- 1 root root 1, 9 Oct 12 09:12 /dev/urandom
    • c: character devices, not files: nothing is stored on the disk
    • 1, 3: the driver (major 1) and the device (minor 3) that answer the read
    ln -s

    A shortcut

    Why it matters

    Links are everywhere in a Linux system: /bin is a link to /usr/bin on modern distributions, /proc/self is a link, and most configuration of services is turned on by creating one.

    ln -s TARGET LINK_NAME
    $ ln -s notes.txt shortcut.txt  # create the link
$ ls -l
-rw-r--r-- 1 student student 18 Oct 12 09:12 notes.txt
lrwxrwxrwx 1 student student  9 Oct 12 09:15 shortcut.txt -> notes.txt
$ cat shortcut.txt  # reads notes.txt
buy milk
call mom
$ readlink shortcut.txt
notes.txt
    • ln -s creates a soft link (symbolic link): a shortcut to TARGET
    • l: the type is link, ls -l shows where it points
    • the link does not hold the data, it holds a path: its size is 9, the length of notes.txt
    • the target can be a file or a folder, the path absolute (/usr/share/doc) or relative

    Following links

    $ ln -s shortcut.txt link.txt  # a link to a link
$ cat link.txt
buy milk
call mom
$ ln -s /usr/share/doc docs
$ ls docs/  # into the folder
bash  git
    • a link can point to another link: the kernel follows them all, until it finds a real file
    • a link to a folder works like the folder: ls, cd
    • a loop (a -> b, b -> a) never reaches a file: Too many levels of symbolic links
    • ls -l, readlink and rm do not follow: they work on the link itself
    Where the path starts

    Broken links and relative paths

    $ rm notes.txt  # delete the target
$ ls -l shortcut.txt
lrwxrwxrwx 1 student student 9 Oct 12 09:15 shortcut.txt -> notes.txt
$ cat shortcut.txt
cat: shortcut.txt: No such file or directory
    • deleting the target does not delete the links to it
    • the link still holds its path, but nothing is there: the link is broken
    • ln -s does not check that the target exists

    A relative target starts from the folder of the link

    $ cd /home/student
$ ln -s notes.txt backup/wrong.txt  # from backup/
$ cat backup/wrong.txt
cat: backup/wrong.txt: No such file or directory
$ ln -s ../notes.txt backup/right.txt  # go up
$ cat backup/right.txt
buy milk

    Write a relative target as if you were in the folder of the link

    Not from your current directory: the kernel resolves the path when the link is used, starting from where the link is.

    Moving links

    you moverelative link (rel.txt -> notes.txt)absolute link (abs.txt -> /home/student/project/notes.txt)
    the link alone, to another folderbreaks: the path now starts from the new folderstill works
    the whole folder, link and target togetherstill works: they moved togetherbreaks: it points to the old place

    Relative links for files that travel together (a project, an archive); absolute links for files that stay in place (/usr/share/doc, /etc/...).

    Check yourself

    You run ln -s notes.txt backup/n.txt from your home directory, where notes.txt is. Does cat backup/n.txt work?

    Virtual files made by the kernel

    /proc: the process file system

    $ ls -l /proc/uptime  # the size is 0
-r--r--r-- 1 root root 0 Oct 12 09:12 /proc/uptime
$ cat /proc/uptime  # but it has contents
244699.78 368114.32
$ readlink /proc/self  # the PID of readlink
4325
    • /proc is a virtual file system: every process has a folder named after its PID
    • nothing is stored on the disk: the kernel writes the contents when a process reads the file
    • /proc/self is the folder of the process that reads it: ls /proc/self lists the folder of ls
    /proc/<PID>

    Inside a process

    $ cat /proc/self/status
Name:     cat
State:    R (running)
Pid:      4330
PPid:     4100
Threads:  1
$ echo $$  # the PID of the shell
4100
$ ls -l /proc/self/fd
lrwx------ 1 student student 64 Oct 12 09:12 0 -> /dev/pts/0
lrwx------ 1 student student 64 Oct 12 09:12 1 -> /dev/pts/0
lrwx------ 1 student student 64 Oct 12 09:12 2 -> /dev/pts/0
lr-x------ 1 student student 64 Oct 12 09:12 3 -> /proc/4331/fd
    • the PPid of cat is the shell: the shell called fork and exec to start it
    • 0, 1 and 2 point to /dev/pts/0, the terminal: it is both the keyboard and the display
    • ls opened the folder it lists at the first free index, 3; a redirect changes these links: with > out.txt, 1 points to out.txt
    • ps, top, pstree and lsof -p PID do not ask the kernel directly: they read /proc; only the owner (or root) can look inside fd/
