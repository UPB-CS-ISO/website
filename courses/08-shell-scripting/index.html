    A programming language, added on top

    The shell runs commands

    Why it matters

    A script automates what you would type: backups, building a project, renaming 300 files. Every line of it is still a command line: words, separated by spaces. Remembering this explains almost every mistake of this lecture.

    backup.sh

cp ~/notes.txt ~/backup/
echo "backup done"

    or you save them in a file, and bash runs them for you

    • the shell was made to run commands: read a line, split it into words, run the command
    • a shell script is a file with command lines; the shell runs them one after another
    • variables, conditions, loops and functions were added on top: everything is still a command line

    Running a script

    ./backup.sh or bash backup.sh

    ./backup.sh asks the kernel to run the file: it needs x and reads #!. bash backup.sh runs bash, which only reads the file.

    $ chmod +x backup.sh  # once: the execute permission

    Common mistake

    backup.sh instead of ./backup.sh

    Without a /, the shell searches the name in PATH, and the current folder is not in PATH: bash: backup.sh: command not found.

    Instead: write the path, ./backup.sh, or run bash backup.sh.

    Running a script with source

    source backup.sh: in your own shell

    source backup.sh (or . backup.sh) starts no new process: your shell reads the file and runs its lines itself, as if you typed them. What the file changes stays in your shell.

    Internal Field Separator

    IFS: where the shell cuts

    IFS is a variable of the shell; its characters are the separators. By default: space, tab and newline. The shell uses it to cut an unquoted $NAME (and, later, the line that read reads).

    $ printf '%q\n' "$IFS"
$' \t\n'

    printf '%q' shows the invisible characters: a space, \t (tab), \n (newline).

    IFS = spacetabnewline

    Splitting a variable

    An unquoted $x is cut at IFS

    Before running printf '[%s]\n' $x, the shell does three things:

    1. replace: $x becomes its value, Alice Smith:20
    2. cut: the value is cut at the characters of IFS (by default: space, tab, newline); every piece becomes a separate word
    3. run: printf gets the words Alice and Smith:20
    $ x="Alice   Smith:20"
$ printf '[%s]\n' $x
[Alice]
[Smith:20]
$ echo $x
Alice Smith:20

    printf '[%s]\n' prints every word it gets between [ ], one per line. echo also gets 2 words and prints them with one space: the 3 spaces are lost.

    Two kinds of separators

    The characters of IFS do not all cut the same way. Space, tab and newline are the exception: they are blanks, and the shell treats them gently.

    In IFSSeveral in a rowAt the start or the endExample
    space, tab, newline (the blanks)one cut: a b → a bdropped: ␣␣a␣b␣␣ → a bIFS default, x=" a b " → [a][b]
    any other character, e.g. : ,every one cuts: a::b → a "" b, an empty word in the middleat the start: an empty first word, :a → "" a; at the end: nothing, a: → aIFS=:, x="a b::c" → [a b][][c]

    A blank that is not in IFS is a normal character: with IFS=:, the space in a b does not cut, a b stays one word.

    Many spaces are one cut

    Spaces are special

    The two kinds of separators in one script: first the blanks (many in a row are one cut, the ends are dropped), then : (every one cuts, :: makes an empty word).

    Quoting and IFS

    Quotes keep one word

    IFS cuts an unquoted value. Quoted, "$x" is always one word, whatever IFS is, with its spaces.

    $_

    Quotes say "one word": write "$NAME" in quotes, unless you want it cut.

    read syntax

    read: one line from stdin into variables

    read is a built-in of the shell: it waits for a line (until Enter) and puts it in variables.

    WriteMeans

    -r, IFS=, and pipes

    The pitfalls of read

    By default, read does not give you the line exactly as it is in the file. It changes it in two ways, and each one has its own fix:

    The line in the fileread l givesWhyThe fix
    C:\new\tempC:newtemp\ is an escape for read: it removes it-r (raw): keep the \
    two spaces two spacesthe spaces at the start and at the end are in IFS: read cuts themIFS= (empty), only for this read: nothing is cut

    Both fixes together read a line exactly as it is: IFS= read -r line. A third trap is not about the text: after a |, read runs in a copy of the shell and its variables are lost.

    One parenthesis runs a command, two compute

    The shell builds the text, bc computes

    Decimals with bc

    bc is a calculator program: it reads the expression from stdin and prints the result. The shell only builds the text of the expression.

    $ echo "7 / 2" | bc  # scale=0: no decimals
3
$ echo "scale=2; 7 / 2" | bc  # 2 decimals
3.50
$ echo "7 / 2" | bc -l  # -l: scale=20 and the math functions
3.50000000000000000000
$ echo "sqrt(2)" | bc -l
1.41421356237309504880

    scale is the number of decimals bc keeps after a division; it starts at 0. Set it in the text you send (scale=2;), or start bc -l: scale=20, plus s(), c(), a(), l(), e() (sine, cosine, arctangent, logarithm, exponential).

    Function syntax

    A function is a new command

    A command prints, and ends with an exit code

    Output or exit code

    A function, like any command, has two ways to answer: the output (text, the data) and the exit code (success or error). The data is printed and captured with $(...); return N is not the data.

    It prints and ends with an exit code, nothing more

    After an error

    A failed command does not stop the script

    When a command fails, bash prints its error and runs the next line, as in the terminal. A script that goes on can do the right thing in the wrong place.

    Run something only when a command fails

    Check it yourself: || and if !

    || and if ! run something only when a command fails: the script can stop there, with an exit code that says it failed.

    save.sh
    #!/bin/bash
# save the photos
mkdir -p backup || exit 1
cd photos || exit 1
cp *.jpeg ../backup/ || exit 1
echo "photos saved"
    Common mistake

    A check after every command

    Every command that may fail needs its own || exit 1, and one is easy to forget.

    Instead: let bash check all of them: strict mode, in the next chapter.

    errexit

    set -e: stop at the first error

    set -e, on a line near the top of the script, stops the script at the first command that fails, with the exit code of that command.

    A checked failure is allowed

    When set -e does not stop

    A command whose exit code is checked may fail: set -e lets it fail, and the script goes on. That is how you allow a failure.

    Line, with set -eWhen its first command fails
    cd photoz🛑 the script stops
    cd photoz || exit 2exit 2 runs: you choose the exit code
    grep -q mango fruits.txt || echo "none"✅ echo runs, the script goes on
    if grep -q mango fruits.txt; then✅ if runs else; the same for while and until
    ! grep -q mango fruits.txt✅ the script goes on
    Common mistake

    ((n++)) stops the script

    With set -e, n=0; ((n++)) computes the old value of n, 0: ((...)) ends with 1, and the script stops without a message.

    Instead: count with n=$((n + 1)).

    Check yourself

    With set -e, which line stops the script when grep finds nothing?

    nounset

    set -u: unset variables are errors

    Without set -u, a variable that is not set is an empty text, and a typo in its name goes unnoticed. With set -u, it is an error that stops the script.

    set -u and the parameters

    $1 is not set when the script gets no parameters: set -u stops the script with an error that does not help the user. $# is always set: check it before you use $1.

    A pipe fails when any of its commands fails

    set -o pipefail

    A pipe ends with the exit code of its last command: when grep fails but wc works, set -e does not see the error. With pipefail, the pipe ends with the exit code of the last command that failed.

    $ grep kiwi nope.txt | wc -l
grep: nope.txt: No such file or directory
0
$ echo $?
0
$ set -o pipefail
$ grep kiwi nope.txt | wc -l
grep: nope.txt: No such file or directory
0
$ echo $?
2
    Strict mode, on the line after the shebang

    All three: set -euo pipefail

    OptionNameWhat it does
    set -eerrexitstops at the first command that fails, outside a condition
    set -unounseta variable that is not set is an error, not an empty text
    set -o pipefailpipefaila pipe fails when any of its commands fails
    set -xxtraceprints every command before it runs, like bash -x

    set +e (with +) turns an option off again. Start your scripts with the first three: a mistake stops the script, it does not go on in the wrong place.

    backup.sh
    #!/bin/bash
set -euo pipefail
mkdir -p ~/backup
cp ~/notes.txt ~/backup/

    Remember commands now, run them later

    trap syntax

    trapthe command
    'rm -f "$tmp"'what to run, in single quotes
    EXITwhen to run it
    • trap runs nothing now: bash remembers the commands
    • the single quotes keep $tmp as it is: it is replaced when the trap runs
    • trap -p lists the traps, trap - EXIT forgets one
    WhenThe commands run
    EXITwhen the script ends, however it ends: after the last line, at exit, or stopped by set -e
    ERRafter every command that fails, where set -e would stop
